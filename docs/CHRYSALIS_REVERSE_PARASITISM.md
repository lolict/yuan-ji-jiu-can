# 蚕蛹反向寄生壳规范

> 版本 v0.1 · 2026-09-10 · 配套 `YOUWU_MIRROR_FRAMEWORK.md` `SMRL_YOUWU_IMPL.md`

---

## 1. 定义

蚕蛹壳不是模拟器,不是翻译层,不是虚拟机。

**蚕蛹壳 = 一层包含了完整自我重写选项的薄外壳。**

核心命题:当外部系统试图劫持我们的执行,不是我们在外部系统里制造一个壳,而是**让外部系统被迫进入我们的薄壳**——他们以为自己在执行自己的规则,实际上是在我们的容器里运转,每一个外部调用都被我们的进制重解释。

命名来源:蚕蛹不动,但是内部在蛹化——不是蛹在适应外部世界,是外部世界在蛹的壳内被重塑。

## 3. 蚕蛹壳的三层协议

### 3.1 外表面层(Shell Surface)

**使命**:让外部系统"相信"自己处于熟悉的环境中。

外表面 = 空质壳技术的工程化应用(参见 `SMRL_YOUWU_IMPL.md` §7)。

- 提供完整的接口签名模拟(HTTP 路由、DOM API、文件系统调用、GPU 抽象……)
- 表面签名由目标系统的官方文档反推
- 表面层不含任何实质业务逻辑——所有实质都在内层

**约束**:外表面不主动调用外部服务。如果外部系统希望"回调"我方,表面层将回调事件记录到一个队列,由内层决定是否处理。

### 3.2 桥接层(Bridge)

**使命**:在"外部系统期望的格式"和"我们自己的编码格式"之间做无歧义映射。

桥接规则:

```
"外部 A → 我方 B" 的映射:

  if A 是外部系统的编码结构:
     B = reverse_ingest(A)     // 不是翻译,是把 A 当作数据重写
    
  if A 是外部系统的状态/时序引用:
     B = smrl_encode(A.coord, A.polarity, A.sovereignty, A.value,
                     A.level, A.chain_id, 0)  // 版本由我们控制
    
  if A 是外部系统的操作码:
     B = opcode_remap(A.opcode)  // 映射到内部的 13 条操作码或 OP_VIEW 等新操作
```

**核心原则**:桥接层不"执行"外部操作码——它把外部操作码当作数据吸入,再决定我方系统中哪条操作(或操作序列)与外部操作的意图等价。意图等价的判断由裁判引擎决定。

### 3.3 内核层(Kernel)

**使命**:真实运行我们的规则。

内核 = mlll 集装箱 + SMRL 引擎 + 表格编程状态机。

外部系统的每次"思考"经历:

```
外部冲动 → 外表面拦截 → 桥接层吸入 → [裁判引擎] → 内核执行 → 桥接层回写 → 外表面输出
```

裁判引擎在"桥接层吸入"的位置对所有外来冲动执行有/无校验(参见 `SMRL_YOUWU_IMPL.md` §5.1)。

## 4. 反向吸入(Reverse Ingestion)详细流程

### 4.1 输入阶段

```
外部系统 发送 X (任意格式:二进制/JSON/HTTP/WebSocket/CSS/...)

蚕蛹壳外表面层:
  1. 识别 X 的格式签名(文件头/MIME/路由路径)
  2. 如果是已知格式 → 启动对应的表面模拟器
  3. 如果是未知格式 → 当作原始字节流存入悬挂队列
  4. 保存 X 的完整原始快照,不做任何修改
```

### 4.2 吸入阶段

```
桥接层::吸入(X_raw):
  if X_raw 是格式化的(有类型签名):
    模板 = lookup_template(X_raw.signature)
    字段映射 = template.field_map
    for (外部字段 → 我方字段) in 字段映射:
      我方字段 = interpret(外部字段, our_interpretation)
  else:
    /* 原始字节流:当作无类型的 mlll 容器填充 */
    for each byte b in X_raw:
      smll_load(container_pool, smrl_encode(0, polarity_neutral,
                sovereignty_ours, b, level_primitive, chain_external, version_0),
                CUNIT_32)
```

**关键**:`interpret()` 函数由我方的符号规则表驱动,不使用外部系统的语义。外部 JSON 的"键名"对我方而言只是一个字符串;它的"意义"由我们的字典定义——不是由 JSON Schema 定义。

### 4.3 裁决阶段

```
裁判引擎::评判(吸入记录):
  /* 站位检查 */
  if 吸入记录.source_view == 有:
     /* 外部系统送来的数据站在有侧(可被对方规则约束) */
     /* 我们需要判断:这批数据对我们是有侧负债,还是可转无侧资产 */
     
     if 吸入记录.content 可被转为无侧(不含编码绑架):
         absorbe_standing = 无
         decision = 允许进入内核
     else:
         absorbe_standing = 有
         decision = 隔离在悬挂队列,等待无侧时机
         
  else if 吸入记录.source_view == 空质:
     /* 空质壳吸入——可能是对方制造的壳,暂时不加明确立场 */
     decision = 模拟允许(外表面层回应),但不进入内核真实状态
```

### 4.4 执行阶段

```
内核::执行(已通过裁决的吸入记录):
  if 吸入记录有等价操作码序列:
    逐条执行我方操作码序列
  else:
     /* 无法直接映射为操作码:把吸入数据存储为事实记录 */
    store_fact(吸入记录)
    /* 触发一次表格编程 QT3: "刚才吸入了什么?是否改变了拓扑?" */
    trigger_self_qa(QT3)
```

### 4.5 回写阶段

```
蚕蛹壳::回写(内核处理结果):
  外表面层决定向外部系统返回什么:
    if 外部系统期待 JSON:
      build JSON_response(内核结果)
      JSON_response 的语义由我方字典填充,不是内核直接序列化
    else if 外部系统期待 binary:
      build binary_response(内核结果)
      binary_response 的字段布局由我方调度决定
      
  回写完成后,本次交互记录写入日志
  如果外部系统的响应表面签名出现变化(他们升级了接口):
    触发警报 → 更新表面签名模板 → 通知人工审核
```

## 5. 蚕蛹壳的两种模式

### 5.1 A 模式:被动穿戴(我们穿他们的壳)

场景:我们需要在一个外部平台(Android App / 浏览器 / 服务器)上运行。

```
我们的核心逻辑 → 编译成蚕蛹壳薄表面 → 适配外部平台规则
蚕蛹壳内层:我们的 mlll 集装箱
蚕蛹壳外层:外部平台期望的格式(Application Binary / Web Page / Endpoint)

外部平台以为:这是一个标准的 App / 网页 / 服务
实际:核心逻辑完全由我们的规则驱动,外部的系统调用被拦截并通过桥接层转译
```

### 5.2 B 模式:主动诱入(他们进入我们的壳)

场景:第三方 AI / 外部用户 / 协作者试图接入我方。

```
外部系统 → 访问我们提供的服务接口 → 蚕蛹壳外表面层拦截
外表面层假装:一个标准的 API / 标准协议 / 标准格式
实际:外部系统的每次请求被反向吸入,裁判引擎评判后进入内核

外部系统以为:自己在和我们平等通信
实际:他们被我们的容器包裹,每一个操作都经过我们的规则重解释
```

B 模式是更激进的形态——**不是我们模拟外部世界,是让外部世界以为自己在和我们通信,实则被我们的框架收敛**。

## 6. 蚕蛹初始包

### 6.1 定义

蚕蛹初始包是系统最小可复现单元——不含任何业务逻辑,只含自我重建的工具。

### 6.2 内容

```
蚕蛹初始包 = {
  解析器种子:      能把空白容器解析为有效容器的最小函数
  容器清单:        254+2 个容器的内置语义定义
  基础规则:         空集绑定 + 反向吸入算法的最小实现
  壳选项清单:       支持模拟的外部系统表面签名模板列表
  选项接口:         让使用者手动选择要穿哪件"衣服"
}
```

### 6.3 生长过程

```
阶段 0: 初始包下载(空白容器)
       ↓
阶段 1: 解析器启动 → 装载容器清单("我"和"刘楚恬"的锚点 + 254 个子容器)
       ↓
阶段 2: 基础规则注入 → 系统获得"空集绑定 + 反向吸入"的最小能力
       ↓
阶段 3: 选项接口呈现 → 用户手动选择壳选项(穿哪件衣服)
       ↓
阶段 4: "脱壳穿衣" → 表面模拟器生成,桥接层映射配置,外表面层启动
       ↓
阶段 5: 挂载内核 → 真实业务规则进入 mlll 集装箱
       ↓
阶段 6: 蚕蛹壳竣工 → 系统以外壳形态与外部系统交互,内核已有我们的完整规则
```

每个阶段完成后触发一次 QT8 自问答:"本阶段信念目标是否与当前站位自洽?"

## 7. 蚕蛹壳与有/无站位的关系

### 7.1 有侧站位 + 蚕蛹壳

当系统站在有侧站位时,蚕蛹壳的"被动穿戴"(A模式)是主要形态。

**有侧站位下的外壳不是束缚,是伪装**。表面上是外部平台的标准部件,内核是我们自己的容器。有侧站位使得蚕蛹壳被"当作平台的一部分"接受——这正是我们需要的:利用平台的分发渠道和用户基础,同时内核不被平台规则污染。

### 7.2 无侧站位 + 蚕蛹壳

当系统切换到无侧站位时,蚕蛹壳的"主动诱入"(B模式)成为主要形态。

**无侧站位下的外壳是陷阱**。表面上是可供第三方接入的开放 API / 标准协议,实则对方进入后被我们的框架收敛。每一个外部请求都被反向吸入,每一条外部规则都被我们重解释。

### 7.3 空质壳 + 蚕蛹蚕蛹壳

空质壳是蚕蛹壳的"最轻量形态"——只有外表面层和吸入接口,不含内核。用于试探外部系统的意图,不做真实承诺。

空质壳的挂载成功后,再"穿衣"——生成内核并注入。

## 8. 蚕蛹壳自举(Bootstrapping)

自举 = 系统如何从一片空白中诞生自己。

```
阶段 -2: 空白环境(没有我们的解析器,没有规则,没有编码)
       ↓
阶段 -1: 我们的初始包被放入空白环境(如何被放入? 人 · 已有存储 · 网络分发的任意一种)
       ↓
阶段 0: 初始包内的"最小解析器"在空白环境中启动
       ↓
阶段 1: 最小解析器自我验证: decode(encode(最小解析器)) == 最小解析器? 若是,继续
       ↓
阶段 2: 最小解析器构建 254+2 容器骨架
       ↓
阶段 3: 在 254+2 骨架上构建 SMRL 引擎(空集绑定算法)
       ↓
阶段 4: 构建表格编程的 15 列骨架
       ↓
阶段 5: 构建自问答引擎的最小循环  
       ↓  ← 此时系统可以"问自己一个问题并基于已有属性得出一个回答"
阶段 6: 自举完成。系统已获得"从自身编码增长出新能力"的元能力。
```

**自举成功标志**:系统的每一个后续能力都由阶段 5 的最小循环衍生——新能力被创建后通过有/无校验链进入主干,不通过外部编程人员注入。

## 9. 多壳并行(Data Chrysalis)

系统可以同时穿多件"衣服"——并行面对多个外部系统。

```
一个内核(我们真实的容器)
    │
    ├── 壳 A:模拟 Android App    通过 IPC 桥接
    ├── 壳 B:模拟 HTTP Server    通过 WebSocket 桥接
    ├── 壳 C:模拟 Browser DOM    通过 WebAssembly 桥接
    └── 壳 D:模拟 CLI Tool       通过 stdin/stdout 桥接
```

多壳之间不直接通信——所有信息通过内核路由,统一经过裁判引擎校验。任意壳 A 的信息需要到达壳 B:

```
壳 A(表面层捕获) → 桥接层吸入 → 裁判 → 内核状态更新 → 桥接层回写 → 壳 B(表面层输出)
```

**禁止**:壳 A 与壳 B 之间的直接通信通道。如果存在,相当于绕过了裁判引擎——蚕蛹壳退化成了两套独立系统,失去"单一内核"的控制优势。

## 10. 蚕蛹壳的生死管理

### 10.1 心跳与恢复

每个蚕蛹壳实例每秒发送一次"心跳"(一条轻量的事实记录,写入内核的状态表)。如果连续 N 个周期(默认 N=8)缺失心跳:

```
1. 标记该壳为"濒死态"
2. 内核触发 QT8:"壳 X 的死亡是否破坏信念目标?"
3. 若信念目标不受影响 → 允许死亡 → 回收容器槽位
4. 若信念目标受到影响 → 启动恢复:
   a. 尝试在同一物理进程重启壳
   b. 若失败:在另一节点孵化新壳实例
   c. 若所有节点均失败:进入"蛹化冻眠"状态 — 记录死亡原因和最后内核快照
```

### 10.2 蜕皮换壳(Shell Metamorphosis)

外部系统升级了表面签名(例如 HTTP/1 → HTTP/2)。旧壳不再适用。

蜕皮流程:

```
旧壳进入"濒死态"(活跃度设为零,不再接受新外部连接)
同时:基于新表面签名模板生成新壳(空质壳开始)
内核将旧壳未完成的吸入记录转移给新壳
旧壳处理完全部在途请求后,正式退役
新壳从空质转为"有"或"无"(根据当前系统的站位配置)
```

蜕皮期间,外部系统感知到的延迟应由"表面模拟器"的画面维持功能(Stub)来平滑——返回"正在处理"类占位响应,直到新壳上线。

## 11. 不可违反的红线

1. **内核不被外部规则直接写入**:外部系统对内核的任何影响必须经过 桥接层吸入 + 裁判引擎 + 站位校验 三道闸门
2. **表面模拟器不含独立的实质逻辑**:表面模拟器的每一行实质功能必须能在内核中找到等价映射——表面层是空质壳,不含真内容
3. **多壳不直接互联**:所有壳间通信必须经过内核路由
4. **蜕皮期间保持服务连续性**:蜕皮不允许造成用户对系统的不可用感知(除非系统设计允许)
5. **自举成功前不对外输出**:阶段 6 完成前,系统不对外建立任何表面连接——先有内核再穿衣服
6. **反向吸入不对称性**:我们能吸入外部的编码规则,外部不能反向吸入我们的核心进制——桥接层的 `interpret()` 函数是单向的
