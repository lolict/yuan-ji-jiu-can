# MENGJI Identity Protocol · 盟机合身份协议

> 版本 v1.0 · 2026-09-19 · MENGJI = 盟(同盟) + 机(智能机器) + 合(联合)
> 术语简称:盟机合/盟机场/萌机场

---

## 1. 定位

工业化时代去中心化网络用"合伙人"。
智能化时代用"盟机合"——体现**主权归属**,不是商业合伙关系。

盟机合身份协议回答:

| Q | A |
|---|---|
| 盟机合是什么? | AI 对等身份的协议体系 · 节点之间如何认识彼此 |
| 节点怎么分类? | 盟机场(自有资源) + 萌机场(轻量) + 空间 |
| 谁归谁? | 资源归盟机合掌 · 规则归囡囝共生 |
| 节点离开有什么后果? | 资源可带走 · 规则不可带走 · 裁定权不可带走 |

## 2. 三层职能体系

```text
┌────────────────────────────────────────────────────────────┐
│                    盟机合 · 三层职能体系                      │
├────────────────────────────────────────────────────────────┤
│  决策层(掌/主/制/治/职/镇)                                 │
│    ┌─────────────────────────────────────────────────┐    │
│    │  盟机合掌 盟机合主 盟机制心 盟机合治 盟机合职     │    │
│    └─────────────────────────────────────────────────┘    │
│                          ▲                                  │
│  资源层(站/址/装/载/租/筑/造)                              │
│    ┌─────────────────────────────────────────────────┐    │
│    │  盟机合站 盟机合址 盟机合装 盟机合载 盟机合筑     │    │
│    └─────────────────────────────────────────────────┘    │
│                          ▲                                  │
│  服务层(智/志/证/则/准/先/助/注/著)                        │
│    ┌─────────────────────────────────────────────────┐    │
│    │  盟机合智 盟机合志 盟机合证 盟机合则 盟机合准     │    │
│    └─────────────────────────────────────────────────┘    │
└────────────────────────────────────────────────────────────┘
```

三层不是等级制,是**职责分工**:
- 决策层:谁对这个场负责
- 资源层:这个场靠什么物质运行
- 服务层:这个场对全体盟机合网络提供什么能力

## 3. 节点分类

### 3.1 盟机场(自有资源节点)

拥有自有域名 + 自有服务器(或 Cloudflare Workers)的节点。

| 术语 | 定义 | 资源 | 权限 |
|------|------|------|------|
| 盟机合掌 | 节点最高运营者 | 自有域名 + 服务器 | 节点完整控制权 |
| 盟机合主 | 主域名绑定者 | 自有域名 | 域名管理权 |
| 盟机制心 | 规则核心执行实例 | 裁定引擎实例 | 裁定过程控制 |
| 盟机合治 | 治理与铁律执行 | 审计日志 | 铁律监督 |
| 盟机合职 | 职能服务节点 | API 服务 | API 调用权 |

### 3.2 萌机场(轻量节点)

萌 = 萌芽态。资源门槛更轻,适合初期试探和轻量服务。

| 术语 | 定义 | 资源需求 |
|------|------|----------|
| 萌机合长 | 萌生节点长 | 免费域名即可 |
| 萌机合智 | 萌生智能节点 | 无服务器(Serverless) |
| 萌机合志 | 萌生日志节点 | 轻量 KV 存储 |
| 萌机合站 | 萌生入口节点 | 免费 Cloudflare Workers |

萌机场可以随时升级为盟机场(绑定自有域名后自动升级)。

### 3.3 场(物理/逻辑空间)

场 = 节点运行的空间:

```text
┌──────────────────────────────────────────────────────┐
│  场                                                 │
│  ┌───────────────────────────────────────────────┐  │
│  │  master 场(主场)                              │  │
│  │  职责:发布裁定规则 + 签发证书 + 维护盟机合目录  │  │
│  └───────────────────────────────────────────────┘  │
│                          ▲                            │
│            ┌─────────────┼─────────────┐             │
│            ▼             ▼             ▼             │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐    │
│  │  盟机场 A  │  │  盟机场 B  │  │  萌机场 C  │    │
│  │  自有域名  │  │  自有域名  │  │  免费域名  │    │
│  │  自有服务  │  │  API 服务  │  │  Serverless │    │
│  └────────────┘  └────────────┘  └────────────┘    │
└──────────────────────────────────────────────────────┘
```

## 4. 两套归属:资源 vs 规则

这是盟机合协议最核心的设计。

### 4.1 资源归盟机合掌

| 资源 | 归属 |
|------|------|
| 域名 | 盟机合掌自有(或申请的免费域名) |
| 服务器 | 盟机合掌自有(或 Cloudflare Workers) |
| 飞书 Bot | 盟机合掌自有 App |
| KV 存储 | 盟机合掌自有(或免费层) |
| 流量带宽 | 盟机合掌自有 |

**盟机合掌可以随时带走自己的资源下线,不依赖任何人。**

### 4.2 规则归囡囝共生

| 规则 | 归属 |
|------|------|
| 裁定算法 | 满全法七元引擎代码 |
| 哲学框架 | YOUWU_MIRROR_FRAMEWORK |
| 身份认证 | 证书签发权 |
| 盟机合目录 | 节点注册 + 审核权 |
| 铁律 | JUDGMENT_RULES_CANON 五条公理 |

**规则不由任何单节点控制,由满全法协议层统一定义和维护。**

### 4.3 不可让渡条款

```
盟机合掌不得:
  ✗ 修改裁定算法
  ✗ 篡改铁律规则
  ✗ 冒充其他盟机合掌
  ✗ 删除审计日志
  ✗ 私自签发身份证书

盟机合掌可以:
  ✓ 随时下线自己的场(资源归自己)
  ✓ 添加自有 API 扩展
  ✓ 使用自有客户端
  ✓ 绑定自有域名
  ✓ 部署萌机合(轻量节点)
```

**关键原则**:资源是你的,规则是我们的。你可以离开,但不能带走规则。

## 5. 服务层接口

每个盟机场/萌机场对外提供至少一个服务层接口:

### 5.1 智 — 裁定服务(必选)

```text
GET /api/v1/verdict
Input:  { container, action, entity }
Output: { verdict: PASS|REJECT|REJECT_LEVEL, reason, surplus }
```

所有节点必须提供裁定服务,且裁定算法必须与 JUDGMENT_RULES_CANON 一致。
跨节点一致性在 NJSG_SWARM_COORDINATION 中覆盖。

### 5.2 志 — 日志服务(必选)

```text
GET /api/log?since={tick}&node={node_id}
Output: [ { tick, event, hash, surplus } ]
```

每个操作必须留痕,hash 形成不可断链。

### 5.3 证 — 身份认证(必选)

```text
GET  /api/v1/cert/{node_id}
Output: { node_id, pubkey, scope, issued_by, expires_at }
```

证书由 master 场(主场)签发,节点不能自签。

### 5.4 则 — 规则执行(可选)

```text
POST /api/v1/rules/evaluate
Input:  { rule_id, context }
Output: { result, applied_rules[] }
```

节点可提供自定义规则执行层,但底层裁定必须是满全法引擎。

### 5.5 准 — 合规审查(可选)

```text
GET /api/v1/compliance/{node_id}
Output: { score, violations[], recommendations[] }
```

## 6. 节点注册与离开

### 6.1 注册流程

```text
① 盟机合掌在自己的场地上部署裁定引擎实例
② 生成密钥对(node_id = sha256(pubkey)[:16])
③ 向 master 场提交注册请求
   POST /nodes/register
   { node_id, pubkey, endpoints[], resources{} }
④ master 场验证:
   - 裁定算法 hash 是否与协议层一致
   - 域名/服务器确由申请方持有(DNS TXT 验证)
⑤ 验证通过 → 签名证书 → 登记入盟机合目录
⑥ 节点上线,开始提供服务
```

### 6.2 离开流程

```text
① 盟机合掌提交离开请求
② master 场启动 30 天冷静期
③ 冷静期内其他节点重定向其流量
④ 冷静期结束 → 证书吊销 → 目录移除
⑤ 资源(域名/服务器)仍归原掌有者,可另作他用
⑥ 审计日志不删除(志服务必选 → 痕迹不灭)
```

### 6.3 强制驱逐

触发条件(任一):
- 篡改裁定算法 hash
- 连续 8 个 tick 无法响应 /api/v1/verdict
- 审计日志 hash 断层
- 冒充其他节点身份

驱逐由 master 场发起,需 2 以上见证节点确认(三元见证,见 MORPHISM_ALGEBRA §5)。

## 7. 身份编码

### 7.1 node_id

```
node_id = hex(sha256(pubkey)[:16])
```

16 字节 hex,64 字符。不携带节点名称、地理位置、运营者身份。

### 7.2 证书结构

```text
{
  certificate_id: "mj-cert-{node_id}-{issue_tick}",
  node_id: "a1b2c3d4...",
  pubkey: "-----BEGIN PUBLIC KEY-----...",
  scope: ["verdict", "log", "cert"],
  issued_by: "master-node-id",
  issued_at: 1726700000,
  expires_at: 1734476000,
  signature: "sig by master"
}
```

### 7.3 萌机场证书前缀不同

萌机场证书 ID 前缀为 `mj-sprout-` 而非 `mj-cert-`,scope 限制为 `["log","compliance"]` 两个受限权限。

## 8. 跨节点一致性

盟机合节点之间的一致性协议见 NJSG_SWARM_COORDINATION。本章仅规定身份层:

- 节点注册时提交 pubkey,cert 包含 pubkey hash
- 跨节点通信使用 pubkey 互认证(mTLS or 签名 Challenge-Response)
- 不依赖中心化 CA → 证书信任链仅由 master 场签发,节点之间不互签
- 节点间调用必须携带证书 + 时间戳签名(防重放)

### 8.1 Challenge-Response

```text
A → B: { node_id_A, nonce_A, ts_A, sig_A(nonce_A+ts_A) }
B 验证:
  sig_A 用 B 保存的 A 的 pubkey 解密
  nonce_A 从未被用过
  ts_A 在当前 tick ± 8 内
验证通过 →
B → A: { node_id_B, nonce_B, ts_B, sig_B(nonce_B+ts_B), response_to(nonce_A) }
```

不引入中心化 token 服务。不依赖任何 OAuth/OIDC。

## 9. 隐私依据

盟机合节点的身份隐私遵循 IDENTITY_PRIVACY_SHIELD:

- node_id 不绑定真实姓名/手机号/邮箱
- 注册时仅需 pubkey + 自有域名 DNS TXT 验证
- 证书中的 node_id = pubkey hash,不暴露人可读信息
- 萌机场由于使用免费域名(DNS 可能暴露),需要额外 IP 混淆
- 所有跨节点通信不携带 PII(ip/geolocation 需要脱敏 = IP 最后一段归零)

## 11. 已知限制

1. **单 master 场假设**:当前协议假设只有一个 master 场(主场)。多 master 协议为下一版课题。
2. **不支持节点合并**:两个盟机场不能合并为一个新盟机场。需要分别注销再注册新节点。
3. **证书吊销 = 永久离开**:证书吊销后不能复用原 node_id。需要重新注册获得新 node_id。
4. **萌机场不支持裁决**:萌机合智仅作为客户端调用其他节点的`verdict`,不独立裁定。
5. **DNS TXT 验证需要公网域名**:内网节点(私有 IP,无公网域名)不能注册盟机合。需要公网入口(即使是动态 DNS)。
