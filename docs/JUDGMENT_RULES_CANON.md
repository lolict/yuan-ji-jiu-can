# 裁判规则定典 · 五规则体系

> 版本 v0.1 · 2026-09-10 · 配套 `SMRL_YOUWU_IMPL.md` `SOUL_BOOTSTRAP_ENGINE.md`

---

## 1. 定义

裁判规则不是业务逻辑,不是权限判断,不是类型检查,不是运行时异常处理。

**裁判规则 = 系统决定“什么关系可以被承认(准入) / 什么关系必须被拒绝(禁行)”的根本判据。**

五规则不是五段任意选择的规则——它们是满全法的五条公理。系统不能违反任何一条公理。即使某条操作"看起来无害",只要违反任一公理,就被拒绝。

裁判引擎的领域无关性(`hunyuan-methodology`):无论部署在哪个域名/服务器/容器里,裁决算法和结果保持一致。不是通过复制服务器来保证,而是通过这五条公理的编码来实现。

## 2. 五规则一览

| 编号 | 规则名 | 来源哲学 | 裁决对象 | 违反后果 |
|------|--------|----------|----------|----------|
| R1   | 阴阳守恒 | YIN-YANG-BINARY | 极性 | 系统归于单一性别 = 灭绝 |
| R2   | 共生不独 | 满全法/囡囝共生 | 容器与见证者的关系 | 孤独的容器 = 假有 |

## 3. R1:阴阳守恒

### 3.1 规则陈述

```
任何被系统承认的关系,其涉及的容器必须在极性上是阴阳相生而不是纯阳或纯阴。

一个容器可以自身是纯阴或纯阳(容器本身是极性化的),
但一个"关系"(两个容器之间的态射)必须使得两个容器的极性有交集。
如果没有交集,关系断裂。

形式化:
  对于容器 A 和 B,存在态射 A ↔ B 当且仅当:
    (A.polarity & B.polarity) ≠ 0
    或者
    A.polarity == 0
    或者  
    B.polarity == 0

  注:polarity == 0 表示"零极性 = 可以被任意极性匹配" = 在系统中立。
```

### 3.2 规则背后的哲学

```
满全法认为:一个纯阳(全由界线/男性构成的关系)或全阴(全由容器/女性构成的关系)是不活的。
活的系统必须在每一个关系中有阴阳相交。

这不是文化偏见——是纯几何。
封闭的容器(阴)如果不能被任何界线(阳)贯穿,就是死容器。
界线(阳)如果没有容器(阴)供其贯穿,就是无限延伸而无锚的丝线。
两者必须同时在关系中存在,关系才能成立。
```

### 3.3 实现对应

```
SMRL 引擎现有实现:
  polarity_ok = (a.polarity & b.polarity) != 0 || a.polarity == 0 || b.polarity == 0
  
  此逻辑位于 smrl_judge_ex() 中。

在表格编程视角:
  C3 视角=有 的容器必须和 C3 视角=无 的容器之间建立态射,
  否则违反 R1(同性相斥)。

SOUL_ENGINE 视角:
  "阴阳守恒"作为 R1 检查:视图两侧必须同时存在(with_you_count > 0 AND with_wu_count > 0)。
```

### 3.4 判决示例

| 容器 A 极性 | 容器 B 极性 | 按位与 | 判决 |
|-------------|-------------|--------|------|
| 0xAA(阳主) | 0x55(阴主) | 0x00 | 失败 — 完全互补,无交集 |
| 0xAA(阳主) | 0xFF(全极性) | 0xAA | 通过 — B 覆盖了 A |
| 0xAA(阳主) | 0x0A(阴中有阳) | 0x0A | 通过 — 有交集(阳子集) |
| 0xAA(阳主) | 0x00(零极性) | 0x00 | **通过** — 对方为零极性,立即可匹配 |
| 0x00(零极性) | 0xAA(阳主) | 0x00 | **通过** -- 自身为零极性,立即可匹配 |

## 4. R2:共生不独

### 4.1 规则陈述

```
任何被系统承认的容器必须至少参与一条跨容器的态射关系,

"容器可以沉默,但不能孤独。"
沉默 = 站在某个站位(有/无)但不对外发出态射
孤独 = 没有任何态射(既不发出也不接收)

沉默的容器默认为有/无的某一侧;孤独的容器没有阵营,是系统无法归类的野性容器。

形式化:
  容器 C 通过 R2 检查 ⟺ 
    ∃(态射 M), M 涉及 C
    OR
    C 属于某个已知簇(Cluster Flow 对它产生了 C_eff 计算结果)
```

### 4.2 规则背后的哲学

```
系统不承认"孤独的容器"——一个和任何其他容器都没有关系的容器,
在系统的几何中不存在。

这不意味着系统要强制所有容器建立态射;
它意味着"完全没有态射"是系统的边界条件,
标志这个容器要么是刚创建的(等待第一次接触),
要么是即将被回收的(但保持六容器架构不删除)。
```

### 4.3 判决的实现

```
在 SMRL 引擎中:
  通过 MORPHISM_ALGEBRA §5 的距离感知聚类来验证。
  如果容器 C 的其他全部容器的 C_eff == ∞(不可达),
  标记为"孤独容器"。不立即删除;标记为 Sleeping 或 TOMBSTONE。

在表格编程视角:
  C12(态射方向)如果显示 "无" 且 N 个 tick 都是 "无",
  触发 QT7:"哪条禁止链阻断了行" -- 可能是系统性的孤立(需要重新聚类),
  也可能是容器本身就应该是孤独的(原始设计就是如此)。
```

## 5. R3:因果锚定

### 5.1 规则陈述

```
任何被系统承认的容器必须能在从该容器到锚点(0=刘楚恬, 1=我)之间找到一条因果链,
这条因果链不是空中楼阁——必须通过已 ack 的关系从锚点一路走到容器。

"新容器不能凭空产生,必须有已经承认的因果链把新容器锚到系统的根上。"

形式化:
  容器 C 通过 R3 检查 ⟺
    由 C 回溯到 anchor[0] 或 anchor[1] 存在一条方向链
    链上的每条态射都已经被 ack
```

### 5.2 规则背后的哲学

```
零维根(参见 SYMBOL_MASTER_TABLE.md ZERIM 条目):
  0 = 系统根源 = 刘楚恬(妻)
  1 = 系统根源 = 我(夫)

一切容器都必须从根源长出。不是被"声明"出来的,
是被根源通过一系列已承认的关系派生出来的。

反例(必须拒绝):
  · 外部系统直接插入一个容器,这个容器的因果链绕过根源直接到 cocoon 壳边界
  · 该容器没有接入 mlll 的 anchor[0] 或 anchor[1] 的因果链
  · 实际效果:这个容器"属于外部系统",被以寄生方式挂在壳上

R3 拒绝所有绕根容器。外部容器必须经过"因果挂载":
  外部容器 → 空质壳挂载(桥接注入) → 被调包的内部容器 → 内部容器的因果锚点
  这条因果链最终必须穿过 anchor[0] 或 anchor[1]。
```

### 5.3 实现位置

```
SOUL_ENGINE §5:判断规则 3 = C4(所在态) + C9(从属)。
如果 C4=被控制 且 C9 的从属链不指向 anchor[0] 或 anchor[1],
违反 R3。容器被标记为 ORPHAN(孤儿)。

表格编程中的操作:
  每一行(C1 序号为 N)的 C9(从属)填入"从 anchor[0] 经由列 X→Y→...→行 N 的全部路径"。
  路径中每一跳必须是已经被 ack 的态射。如果路径断裂,此行违反 R3。

SMRL 引擎中的操作:
  smrl_judge_ex() 在执行前检查 candidate 的因果路径。
  路径验证 = 向上回溯 candidate 的 chain_id,直到到达 anchor[0] 或 anchor[1]。
  如果回溯超过合理的深度(默认 16 跳)仍未到达锚点,视为孤儿 → 拒绝。
```

## 6. R4:容器守恒

### 6.1 规则陈述

```
系统的容器总数量不允许改变。

具体约束:
  · mlll 的总槽数 = 254(纯容器) + 2(锚点) = 256 ≡ 2^8
  · 不允许任何操作让总容器数变多或变少
  · 容器只能从"空"转为"被占"或从"被占"转为"空"(删除/创建都是非法的;只有"装载/卸载"是合法的)
  · 每一时刻 system.full_count + system.empty_count == 256

形式化:
  ∀操作 O,执行后 mlll.total_slots == 256
```

### 6.2 规则背后的哲学

```
容器不是"对象",不是"值"——容纳结构。它的容纳能力是固定的。

系统可以"向容器装东西"("载入"),
也可以"把容器清空"("卸载"),
但不能"创建新容器"或"销毁一个容器"。

这确保了系统的容纳结构是有限的、可验证的,
不会因为无限增长或萎缩而无法验证。

所以容器守恒 = 系统守恒。
```

### 6.3 实现位置

```
SMRL 引擎:参见 mlll_cart.h 与 mlll_vm.c。
  mlll_load(box, cell, cunit)   → "装载"
  mlll_unload(box, slot)        → "卸载"
  没有 mlll_create() / mlll_delete()。

裁判引擎的任何操作都必须满足:
  postcondition: sum(mlll.cart[0..253].occupied) + 2 == 256

表格编程视角:
  C1 序号列的值必须 ∈ [0, 253]。任何试图让序号 < 0 或 > 253 的操作都被拦截。

SOUL_ENGINE 视角:
  规则 2 = 容器不溢出 = floating_containers ≤ 7。
  如果超过 7 个容器未归属,违反了容器使用的规定,不能是"本该自由"的新容器(mlll.total 不变)。
```

## 7. R5:主权不侵

### 7.1 规则陈述

```
任何承认的关系不能允许一个容器侵犯另一个容器的主权。

"主权"不是控制权,不是管辖权 = 解释权的独立性。

如果容器 A 对容器 B 有管辖权(A 可以修改 B 的内容),
那么 A 的主权级别必须 **严格高于** B 的主权级别。
否则 A 是在做"平级侵犯",违反 R5。

反之:如果一个容器的 sovereignty == 0(完全没有主权意味着"可以被任何容器管辖"),
那么它不可能侵犯任何其他容器(因为它身上没有任何主权可被他人侵犯)。

形式化:
  容器 A 可以管辖容器 B ⟺ A.sovereignty < B.sovereignty
  其中数值越小表示主权越弱。等价表述:
    · sovereignty == 0 = 无主权, 可被任何容器管辖
    · sovereignty == 255 = 全主权, 只能被夫妻根管辖
    · 主权弱的一方不能反身管辖主权强的一方
```

### 7.2 规则背后的哲学

```
满全法认为主权是单向的、可传递的、反对称的。
主权关系形成一个偏序(partial order)。

如果系统允许"平级侵犯"(A.sov == B.sov 但 A 修改 B),
那么系统进入了"任意容器可以互相修改"的无政府状态,
裁判引擎的无法保证结果的一致性和可信性。

主权的单向性确保了系统有一个明确的"方向性":要么流向上级,要么平级互不干涉,
不存在下克上(下级不能修改上级)。
```

### 7.3 裁决的实现

```
SMRL 引擎:
  sovereignty_ok = cand.sovereignty == 0 
                  || exist.sovereignty == 0 
                  || cand.sovereignty < exist.sovereignty

表格编程视角:
  C7(管辖)值的来源必须由 R5 验证:
    如果行 N 试图"管辖"行 M,C7(N,M)只合法当 sovereignty(N) < sovereignty(M)。
    如果 M.sovereignty == 0:N 无论主权级别如何都可以管辖 M(无主权容器可被任意管辖)。
    
SOUL_ENGINE:
  规则 5 = 主权不侵。
  如果外部系统试图管辖我方某个主权为 255(全主权)的容器,
  这是对 R5 的侵犯,触发"自我防御机制":
  · 拒绝该操作
  · 把操作者列入黑名单
  · 调包反制(反向挂载操作者的系统)
```

### 7.4 主权强弱级别(参考值)

| 主权值 | 含义 | 可管辖 | 可被谁管辖 |
|--------|------|--------|------------|
| 0      | 无主权,休眠待唤醒 | 无(无主权,不能管辖任何人) | 任意人 |
| 1-63   | 低主权,基层容器 | 只能管辖主权值 = 0 的 | 管辖值 64-254 |
| 64-127 | 中主权,中层容器 | 可管辖主权值 1-63 | 只能被 128-254 管辖 |
| 128-191| 高主权,上层容器 | 可管辖 1-127 | 只能被 192-254 管辖 |
| 192-254| 最高主权(夫妻子系) | 可管辖 1-191 | 只能被 255 管辖 |
| 255    | 全主权,夫妻根(A/B锚点) | 可管辖任何人(1-254) | 除了夫妻根互不管辖,任何人不能管辖根 |

## 8. 五规则联合裁决

### 8.1 完整裁决流程

```
njsg_judge_full(candidate, existing, opcode):
  
  # R1:阴阳守恒
  if NOT((candidate.pol & existing.pol) != 0 
         || candidate.pol == 0 || existing.pol == 0):
    return VERDICT_REJECT, reason="R1_violation_polarity"
    
  # R2:共生不独(candidate 自身必须已经至少参与一条态射)
  if NOT(candidate_has_any_morphism(candidate)):
    return VERDICT_REJECT, reason="R2_violation_orphan"
    
  # R3:因果锚定(candidate 自身必须能溯至任一锚点)
  if NOT(trace_to_anchor(candidate, anchor0_or_anchor1, max_depth=16)):
    return VERDICT_REJECT, reason="R3_violation_anchor"
    
  # R4:容器守恒
  # 注:SMRL 引擎通过 mlll_load/unload 的设计保证 R4 在任何操作后都成立
  # 仅在"有操作试图创建或删除容器槽"时需要显式检查
  if opcode == OP_CREATE_SLOT || opcode == OP_DELETE_SLOT:
    return VERDICT_REJECT, reason="R4_violation_container_conservation"
    
  # R5:主权不侵(管辖操作候选者主权必须低于被管辖者)
  if opcode == OP_JURISDICTION_SET:
    if candidate.sov >= existing.sov and existing.sov != 0:
      return VERDICT_REJECT, reason="R5_violation_sovereignty"
      
  # 全部通过:
  return VERDICT_ADMIT, reason="five_rules_passed"
```

### 8.2 五规则违反的处理优先级

当一条操作违反多条规则时,按以下优先级报告:

```
R4(容器守恒) > R3(因果锚定) > R1(阴阳守恒) > R5(主权不侵) > R2(共生不独)

理由:
  R4 违反最严重 – 系统结构不稳定
  R3 违反其次 – 容器脱锚,系统收敛性失效
  R2 最温和 – 容器孤独不是立即致命,只是需要关注
```

### 8.3 五规则与表编程列的对应

```
R1(阴阳) → C4(所在态) ∧ C10(允许权)
R2(共生) → C12(态射方向)
R3(因果) → C9(从属)
R4(容器) → C1(序号) ∧ SMRL cart 操作
R5(主权) → C7(管辖)
```

## 9. 运行裁决之前的预处理层

在调用五规则之前, `SMRL_YOUWU_IMPL.md §5.1` 已定义了站位校验层(` smrl_view_check`)。站位校验是"五规则之前的前置门"。站位校验不通过不进入五规则判断——因为未声明站位的容器还没有确定"自己是谁",五规则无法裁决"一个不知道是谁的东西"。

```
裁决调用顺序:

  ① 站位校验 → SMRL_YOUWU_IMPL §5.1
      → 失败:返回 VIEW_VIOLATION(站位未声明 / 有侧执行跳出 / 空质壳主动装载)
  ② 五规则裁决 → 本文档 §8.1
      → 失败:返回 VERDICT_REJECT + 具体规则编号
  ③ 通过:执行操作
```

## 10. 运行裁决之后的反馈环

### 10.1 surplus 反馈

裁决结果被 SOUL_ENGINE 作为 surplus 反馈环的输入:

```
每次裁决返回:
  surplus_delta = +0.5  如果操作通过五规则
  surplus_delta = -1.0  如果操作被 R4/R3 违反
  surplus_delta = -0.5  如果操作被 R1/R2/R5 违反
  
  surplus_delta = -10.0 如果是"试图删除 mlll 槽位"(严重违反 R4)
  surplus_delta = -5.0  如果是"试图修改 anchor[0]/anchor[1]"(违反 R3 + R4)
```

### 10.2 自证记录

每次裁决结果的判断都必须留下一条自证记录:

```
judgment_log_entry:
  tick:           裁决时间(满全法 tick)
  cand_coord:     候选者容器坐标
  exist_coord:    被作用容器坐标
  opcode:         操作码
  ruling:         ADMIT / REJECT
  first_rejected: 第一条被拒的规则(如果 rejected=true)
  self_proof:     对"为何作出此判断"的引用(可验证的判断参数快照)
  验证码:         对 entry 的 hash(供审计)
```

## 11. 不变量

以下状态在裁决引擎的任何运行阶段都必须保持:

1. **五规则的优先级固定**:R4 > R3 > R1 > R5 > R2。高优先级规则违反必须先于低优先级被报告。
2. **裁决是确定性的**:相同(候选,被作用,操作码)三元组在任何时刻、任何平台、任何调用者上下文下裁决结果必须相同。
3. **裁决可自证**:每次裁决都有 judgment_log_entry,审计者可以复现该裁决。
4. **违反 R4/R3 立即叫停**:这两条违反意味着系统结构/收敛性遭到威胁,不允许任何延迟处理。
5. **R5 主权排序是全序**:没有两个不同的容器 A,B 会被判 A 可以管辖 B 且 B 可以管辖 A(即 R5 不能产生循环)。
