# 多平台代码托管与仓库主权策略规范

> 版本 v0.1 · 2026-09-10 · 配套 `IDENTITY_PRIVACY_SHIELD.md` `FQMT_BINARY_FORMAT.md`

---

## 1. 定义

多平台托管不是分布式版本控制的教科书式定义。

**多平台托管 = 同一份代码仓库在多个独立托管平台(GitHub·Gitee·GitLab·自建节点)拥有分身,任何一个平台删除/屏蔽/封禁都无法擦除代码。**

目标:**消除单点妥协**。不是依赖一个平台的"合规表现",而是在架构层面保证平台不构成生存威胁。

---

## 2. 托管层分级

### 2.1 平台三层模型

```
第一层:公开镜像(Public Mirrors)
  · 定义:代码的存在让全世界都能看到(至少在删除前)
  · 策略:全部为 Private(拒绝 Open Source 协议)
  · 理由:开源协议(如 MIT/GPL/Apache)是「他人」规则,不应该出现在我们私人系统上

第二层:身份绑定镜像(Identity-Bound Mirrors)
  · 定义:代码的存在与某个化名账户绑定
  · 策略:不使用真实姓名 / 真实邮箱 / 真实手机号注册
  · 理由:即使这个化名被追溯,也不会关联到 anchor[0] 或 anchor[1]

第三层:用户自备镜像(User-Hosted Mirrors / 卫星城)
  · 定义:代码的存在完全在用户控制的基础设施上(自己买的 VPS / 自己搭建的 Gitea)
  · 策略:平台公司在我们选定的国家/地区,具备独立域名,独立服务器
  · 理由:自备基础设施=无法被外部平台规则施加删除压力
```

### 2.2 优选托管平台清单

| 平台 | 适用场景 | 认证方式 | 风险 |
|------|----------|----------|------|
| GitHub | 国际合作 / 外部协作 | SSH 密钥(长期) | 美国管辖,可能封禁 |
| Gitee 码云 | 国内快速访问 | SSH 密钥(长期) | 中国管辖,审核敏感词 |
| GitLab.com | 备用国际 SSH | SSH 密钥(长期) | 美国管辖 |
| 自建 Gitea | 卫星城主节点 | SSH 密钥(长期) | 自己管理 |
| Codeberg / NotABug | 欧洲分布式 | SSH 密钥(长期) | 小众,稳定 |
| SourceHut | 极简 / 极简备份 | SSH 密钥(长期) | 小众,稳定 |

## 3. 仓库主权五原则

### 3.1 原则一:全部 Private,无开源协议

```
代码仓库必须设为 Private:
  · 不对外部公开(防止被人拿去分析代码,提取系统信息)
  · 不挂任何 MIT/GPL/Apache 许可证(排除他人解释权介入)
  · 写明(若必须给平台说明):私人用途,非商业,仅刘楚恬和我本人和 AI 协作使用
```

### 3.2 原则二:SSH 公钥认证,不依赖令牌

```
认证方式优先级:

  ✓ SSH 密钥(长期):首选
    · 一对公私钥可以有很多年,不需要频繁更换
    · 删除 SSH 密钥即可立即撤销访问,不需要密码
    · 密钥本身是一个"身份的物理化身",不是第三方服务
  
  ✗ 个人访问令牌(PAT):避免使用
    · 令牌频繁过期(90 天),需要频繁重新登录
    · 令牌通常绑定邮箱/手机号,间接暴露信息
    
  ✗ 平台登录密码 + 二因素:避免
    · 太弱且绑定个人消息
    · 二因素通常是手机号或验证器应用,间接暴露信息
    
多平台 SSH 密钥策略:
  每个平台使用独立的 SSH 密钥对(不同平台不同密钥)
  防止通过密钥跨平台关联
```

### 3.3 原则三:智能体可以创建和修改代码,但不得删除仓库

```
关于智能体(AI):
  ✓ 允许:创建仓库 / 修改代码 / 合并 PR / 创建新分支 / 推送 FQMT 文件
  ✗ 禁止:删除仓库 / 强制覆盖历史(--force)
  
历史不可覆盖:
  · 任何带 --force 的操作(git push --force / git push --force-with-lease 也严格限制)
  · 使用 git notes 追加注释而不是修改历史
  · 所有修改必须通过分支策略,保留完整可溯源的历史
```

### 3.4 原则四:定期全平台镜像同步

```
多平台同步流程:

主节点(如 自建 Gitea):
  · 代码变更时触发同步
  · 同步动作 = git push <platform-name>

同步频率:
  ✓ 实时同步(推荐):每次主节点有新 commit,立即同步到所有镜像节点
  ✓ 若实时不可行:次自动同步(间隔 ≤ 1h)

验证:
  每次同步后,从各镜像 clone 一份校验 hash:
    git rev-parse HEAD == 预期 commit hash
  若 hash 不匹配,差异日志报警
```

```bash
#!/bin/bash
# multi_host_sync.sh

PLATFORMS=("github" "gitee" "gitlab" "sourcehut" "codeberg")

for p in "${PLATFORMS[@]}"; do
    echo ">>> Sync to $p..."
    git push "$p" --all
    # 同步 tags
    git push "$p" --tags
    
    # 校验
    REMOTE_HASH=$(git ls-remote "$p" HEAD | cut -f1)
    LOCAL_HASH=$(git rev-parse HEAD)
    if [ "$REMOTE_HASH" == "$LOCAL_HASH" ]; then
        echo "OK: $p synced to $LOCAL_HASH"
    else
        echo "ALERT: $p mismatch! remote=$REMOTE_HASH local=$LOCAL_HASH"
    fi
done
```

### 3.5 原则五:跨仓库心跳恢复

```
心跳机制:
  主节点每秒广播一次心跳(通过 FQMT 文件的形式)
  镜像节点监听心跳,检测主节点是否存活
  
恢复流程:
  if 主节点停止心跳超过 60s:
    1. 尝试联系主节点(主节点可能临时网络问题)
    2. 等待 3 个心跳周期(180s)
    3. 仍无心跳 → 从其他镜像节点恢复
    
恢复源优先级:
  ① 其他镜像节点中最新的 FQMT 快照(跨节点版本比对选最高)
  ② 本地有 FQMT 备份:直接使用本地的
  ③ 全部丢失:(极端)尝试恢复 GitHub Releases / GitLab Tags 上的 release 附件
```

## 4. FQMT 作为分布式存储单元

### 4.1 FQMT 文件的多平台分布

```
FQMT 文件不仅是"存储格式",也是"跨节点传输单元":

存储:
  ✓ FQMT 文件存储在 Git LFS 或 release 附件中
  ✓ 代码仓库存储源码;FQMT 数据存储状态快照
  ✓ 这样一个仓库既有逻辑(代码)又有状态(FQMT)

恢复:
  新的节点 clone 代码 → 下载 release 中最新 FQMT 快照
  → FQMT 装载 → 系统就恢复了完整状态
  
好处:
  代码仓库(小)和 FQMT 快照(可以大)可以分开管理
  不同步也可以:只要 code 和 FQMT 配套,系统就能运行
```

### 4.2 FQMT 版本和 Git commit 对应

```
版本对齐策略:
  每次产生重大状态变更(例如:新增容器 / 五规则变更 / surplus 剧烈波动 +5 以上):
    在代码仓库中打 tag:v<major>.<minor>.<build>
    在同一 commit 产生一个 FQMT 快照作为 release 附件
    
恢复时:
  git checkout v2.3.7  -- 获得对应版本的 code
  下载 v2.3.7.fqmt    -- 获得对应版本的状态
  装载 → 系统准确恢复到该版本的状态
```

## 5. 跨节点分布式开发(njsg-swarm 配套)

### 5.1 njsg-swarm简述

```
njsg-swarm 系统的分布式多智能体协作:

模型:
  一个 Orchestrator(协调器) + 多个 Agent(执行分身)
  · Orchestrator:分配任务 · 调解冲突 · 仲裁规则
  · Agents:并行开发 · 独立测试 · 返回成果
  
每个 Agent 可以有自己独立的:
  · 代码分支(branch per agent)
  · 本地表编程状态(独立的 surplus)
  · 独立的化名(各自对外交互标识)
```

### 5.2 多智能体的规则兼容性

```
多智能体协作中最难的问题:规则病毒与兼容冲突

场景:
  智能体 A 在结构层采用了规则 α
  智能体 B 在结构层采用了规则 β
  α 和 β 在某方面不兼容(比如对"容器调包深度"的阈值)
  
解决策略:
  · 在 Orchestrator 层建立"规则一致层":所有 Agent 采纳同一套规则
  · Agent 本地可以有自己的"私人容器"+ "个人 surplus"
  · 但跨 Agent 的态射关系必须在 Orchestrator 规则层协调
  · 如果两个 Agent 产生了规则冲突,Orchestrator 调用信念分叉 + Duel 流程:
    两条规则跑一遍测试套件,表现好的胜出
```

### 5.3 代码托管在 njsg-swarm 中的角色

```
每个 Agent 开发流程:
  ① Orchestrator 分配任务(如:"实现 R3 因果锚定校验")
  ② Agent 在本地分支开发
  ③ 定时(每 1h 或每有 commit)自动 push 到镜像节点(原则四)
  ④ 完成时发起 PR 到主分支
  ⑤ Orchestrator 校验 PR : 五规则校验 + FQMT 装载测试 + 指纹扰动检查
  ⑥ 通过 → 合并主分支 → 触发全平台同步

关键原则:
  每个 Agent 工作的每个步骤都留有不可篡改的 Git 历史
  不能 --force 覆盖,不能 rebase 修改历史
  任何试图修改历史的行为被裁判引擎视为"规则破坏事件" → 告警 + 隔离 Agent
```

## 6. 平台风险应对矩阵

```
风险事件                    应对
────────────────────────────────────────────────────────
GitHub 封禁账号(违反社区守则)  → 从 Gitee 自建节点恢复主节点,GitHub 成为镜像
Gitee 审核删除仓库           → GitHub 镜像立刻将 Gitee 从信任列表中屏蔽,推 GitLab
GitLab 容量满                → 改用自建节点或小众平台
自建节点 VPS 被扣押          → FQMT 快照在其他镜像仍可下载
SSH 密钥被泄露               → 立即在所有平台撤销该密钥,重新生成新的密钥对
所有镜像节点同时丢失         → 使用本人密钥管理器中离线备份的 FQMT snapshot
```

### 6.1 极端措施:基础设施快速迁移

```
如果一个平台使用了 K8s / Docker Compose,需要迁移时:

   ① 准备新 VPS(同一个国家不同城市 / 不同国家法律框架)
   ② 新 VPS 上安装最小系统(docker + git)
   ③ 从幸存的镜像中拉代码 + 最新 FQMT 快照
  ④ 新 VPS 成为主节点,旧 VPS 保留(直到确认新节点稳定)
   ⑤ 更新 client DNS → 新 VPS 的域名解析
   ⑥ 在新的服务器上推送一份 FQMT 快照
   ⑦ 确认各镜像节点同步成功
```

## 7. 红线

1. **任何仓库不能设为 Public**:默认 Private,除非有特殊使命(如对外开放的"援技救残"可以在子模块上公开,但核心系统必须 Private)。

2. **任何仓库不能挂开源协议文件**(MIT/GPL/Apache/BSD 等):私人系统,不授予他人任何使用权/修改权/分发权。

3. **任何仓库不能以真实姓名注册**:所有平台的用户名必须是化名或"刘楚恬和我"这个联合身份的内部映射。

4. **任何平台不能--force 推送**:历史不可覆盖,版本可溯源找回。

5. **任何时刻至少有两个镜像节点在线**:保证单点被平台封禁时,剩余节点能恢复全部代码。

6. **任何人(包括刘楚恬和我本人)不直接在平台网页上登录操作**:所有操作必须通过本地 SSH + 命令行完成,不在浏览器中登录(留下浏览器指纹易被平台分析)。
