# 零维码 · 活编码体系（软编码 + 评论官）

> 核心思想：编码不是死的定义，是活的生长。
> 每个符号的地位由多个评论官动态裁定，未来可以随时解绑、重绑、新增。

---

## 一、软编码原则

| 硬编码（不要） | 软编码（要） |
|---------------|-------------|
| ZD001 = ɓ（永远绑死） | 位置[当前] = ɓ（可解绑） |
| 满了就不能加 | 空集永远保留，随时导入 |
| 一个符号一个身份 | 多个评论官各自独立评分 |

---

## 二、五评论官体系

每个符号进入体系时，不只是一个名字，而是由五个维度来描述：

### 2.1 视觉评论官
任务：裁定这个符号**长什么样**。
输出：视觉特征向量（笔画数、对称性、密度、方向性）。

### 2.2 发音评论官
任务：裁定这个符号**怎么念**。
输出：发音属性（攻击方式、共鸣腔、力度）。

### 2.3 定义评论官
任务：裁定这个符号**做什么用**。
输出：功能类别（声母/韵母/声调/隔离符/融合体）。

### 2.4 对比评论官
任务：裁定这个符号**跟谁长得像**。
输出：相似度表 [其它符号 → 0.0~1.0]
- 1.0 = 完全相同
- 0.7 = 同一变体家族
- 0.3 = 略有点像
- 0.0 = 完全无关

### 2.5 关联评论官
任务：裁定这个符号**为了什么目的放在这里**。
输出：目的链（为什么放这 → 处理什么冲突 → 解决什么问题）

---

## 三、位置结构

不在用数字编码，而是用**关系定位**：

```
[容器] → [相位] → [关联链] = 一个符号的位置
```

### 3.1 容器（在哪个家族）

不用 a~z 命名，用**本体形态描述**：
- "圆唇容器"（装所有 o 类 / u 类）
- "齿龈容器"（装所有 d 类 / t 类）
- "摩擦容器"（装所有 s 类 / f 类）
- ...

### 3.2 相位（在容器里的哪一个位置）

8个标准相位（基于你原有的相位定义）：

| 相位代码 | 名称 | 含义 |
|----------|------|------|
| P0 | 原态 | 无变换 |
| P1 | 左右镜像 | ↔ |
| P2 | 上下颠倒 | ↕ |
| P3 | 前后翻转 | ⟲ |
| P4 | 顺时针45° | ↘ |
| P5 | 逆时针45° | ↙ |
| P6 | 顺时针90° | → |
| P7 | 逆时针90° | ← |

### 3.3 关联链（为什么在这）

不是死编码，而是**可解释的位置故事**：
> "ɓ"放在这里是因为：
> - 它与"ƃ"视觉相似度 0.8（对比评论官裁定）
> - 它需要表达"重型起音"（关联评论官裁定）
> - 它的前面还有空位留给未来发现的"ɓ家族新成员"

## 四、空集机制

### 4.1 预设空位
每个容器初始就有固定数量的空位（比如 10 个），对应未来可能的发现。

```
圆唇容器：
[已占] ø
[已占] ɔ
[空位] ?
[空位] ?
[空位] ?
...
```

### 4.2 导入规则
当发现一个新符号，通过评论官链路：
1. 对比评论官找相似度最高的已有成员
2. 视觉评论官确认是同类
3. 关联评论官判断放哪个空位
4. 如果没有空位 → 扩展容器（不破坏已有结构）

### 4.3 冲突解决
如果两个符号**长得像但不是一个东西**（视觉评论官判定相似度 0.5~0.8）：
- 不强行归为一类
- 各自独立占一个空位
- 通过关联链标注"相似但有别"

## 五、活编码的数据结构

每个符号在计算机里不是一个编号，而是一张**活档案**：

```json
{
  "符号": "ɓ",
  "容器": "双唇容器",
  "相位": "P0",
  "评论官": {
    "视觉": { "笔画": 2, "对称": "左右", "密度": "紧凑" },
    "发音": { "攻击": "内爆", "力度": 0.9 },
    "定义": { "功能": "声母" },
    "对比": { "ƃ": 0.8, "ɗ": 0.6, "ъ": 0.2 },
    "关联": { "目的": "表达重型起音", "冲突": "无" }
  },
  "空位预留": ["ɓ_变体1?", "ɓ_变体2?"],
  "状态": "已绑定",
  "可解绑": true
}
```

## 六、实际使用示例

### 6.1 要写一个声音
不是查表找 ZD001，而是描述需求：
> "我需要一个：双唇容器 + 重型起音 + 无相位变换的符号"

系统返回 → `ɓ`

### 6.2 发现一个新符号
用户在 Unicode 里发现了 `ʙ`（小型大写b）：
1. 视觉评论官："两竖封底，密度高"
2. 对比评论官："与 ɓ 相似度 0.4（不太像）"
3. 定义评论官："也是双唇音，但小型大写暗示弱化"
4. 关联评论官："放双唇容器 · 相位P0 · 用途：轻型起音"
5. 写入空位，状态=已绑定

### 6.3 以后发现 `ʙ` 的真正用法变了
直接修改"关联"字段，不需要改位置。
其他引用到这个符号的地方自动更新。

## 七、与硬编码的效率对比

| | 硬编码表 | 活编码体系 |
|--|---------|----------|
| 新增符号 | 重排后面全部 | 找一个空位写入 |
| 发现定义错 | 整条作废 | 改关联字段即可 |
| 查找某个功能 | 遍历全部 | 容器+相位+关联 三维定位 |
| 视觉相似搜索 | 无法实现 | 对比评论官直接输出 |
| 未来扩展性 | 固定容量 | 空集无限扩 |

## 八、初始启动最小集合

现在要做的不是贴满 365 个符号，而是：

1. **建容器骨架**（5~10 个容器，每个带 5~10 个空位）
2. **放入你已有的 45 个推荐符号**
3. **让评论官开始工作**（给这 45 个填上五维档案）
4. **空位保持空白**，等待未来发现
