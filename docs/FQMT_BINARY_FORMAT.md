# FQMT · 二进制容器格式规范

> 版本 v0.3 · 2026-09-10 · 配套 `global_interlock.h` `CONTAINER_REPERTOIRE.md`

---

## 1. 定义

FQMT 格式不是序列化协议,不是压缩容器,不是虚拟机镜像。

**FQMT = 系统的自识别二进制包裹——它同时也是在裸机上从文件首字节直接开始执行的入口代码。**

任何一个 FQMT 格式的二进制文件,在文件偏移 0 处的一条 CPU 指令就能确认"这是我们系统的东西,不是别人家的 JSON / XML / Protocol Buffers / ELF / PE"。系统的所有持久化状态、分片传输、备份恢复、跨节点迁移都通过 FQMT。

命名来源:**F**ull(满) **Q**囡囝(共生) **M**ethod(法) **T**ag(标识)。

## 执行入口:魔数即机器码

魔数不是可读文本, 而是不同平台上代表同一语义的真实 CPU 指令序列:

**"CPU 执行进入 FQMT 的第一条指令时, 故意在这里触发异常/陷阱 —— 这就是『我已到达满全法系统入口』的信号。"**

此设计的理由:文件的魔数也同时是加载器执行到的第一条指令。在裸机语境下 FQMT 既可从文件读取识别也可直接跳到入口执行 —— 两种场景使用字节相同的魔数。

### 各平台真实机器码

| 架构        | 魔数(大端序)   | 指令           | 触发效果                  |
|-------------|-----------|----------------|---------------------------|
| x86-64(A)   | `0F 0B 0F 0B` | `UD2; UD2`     | 非法指令异常(#UD)立即停止   |
| x86-64(B)   | `CC CC CC CC` | `INT3; INT3; ×2`| 调试异常(#DB)立即停止      |
| x86-64(C)   | `F3 0F 1E FA` | `ENDBR64`       | CET 合法分支目标标记(如果 CET 不存在立即 #UD) |
| AArch64     | `00 00 20 D4` | `BRK #0`        | BRK 异常立即停止           |
| AArch64(alt)| `E7 F0 DE F0` | `HLT #0x7F0F`   | 调试停机异常               |
| RISC-V 32/64| `73 00 10 00` | `EBREAK`       | EBREAK 立即异常            |
| wasm32/wasm64| `00 61 73 6D`| `\0asm`        | WASM 魔数(语义特殊:模块入口而非陷阱) |

### 选择策略

读取者从偏移 0 读入 4 字节后,按以下顺序判断:

```
  如果在大端序(网络序)下读到的值与 ENDBR64 匹配:
    → 标记 arch = x86-64-CET
  否则如果与 EBREAK 匹配:
    → 标记 arch = RISC-V
  否则如果与 BRK #0 匹配:
    → 标记 arch = AArch64
  否则如果与 UD2×2 或 INT3×4 匹配:
    → 标记 arch = x86-64
  否则:
    → 未知魔数,拒绝解析或尝试按旧版 ASCII "FQMT" 回退(仅对 legacy 支持)
```

### 文件魔数在 FQMT header 中的实际存储

| 文件类型     | header 偏移 0x00-0x03 内容                    |
|-------------|-------------------------------------------|
| 主系统 FQMT  | ENDBR64 或平台对应的魔数(见上表)              |
| 包含完整 IDENTITY_BLOCK 的 FQMT | IDENTITY_BLOCK 的首字节为自身的 `IDNT`(0x49444E54),没有 IDENTITY_BLOCK 时使用系统魔数 |

**Legacy 回退**:版本 ≤ 3 的可能文件使用 `"FQMT"` 文本魔数(0x46514D54)。读取者在看到 `0x46514D54` 后选择 legacy 路径,但标记 deprecation 警告。版本 ≥ 4 的文件强制使用真实 CPU 魔数。

## 2. 文件整体结构

```
┌─────────────────────────────────────────────┐
│                  FQMT HEADER                  │  16 bytes
├─────────────────────────────────────────────┤
│                  CONTAINER #1                 │  变长
├─────────────────────────────────────────────┤
│                  CONTAINER #2                 │  变长
├─────────────────────────────────────────────┤
│                   ... ...                     │  变长
├─────────────────────────────────────────────┤
│                  CONTAINER #N                 │  变长
├─────────────────────────────────────────────┤
│                  PADDING                      │  对齐 16 bytes
├─────────────────────────────────────────────┤
│                  DIGEST TRAILER               │  4 bytes
└─────────────────────────────────────────────┘
```

整个文件是**单序的**——从头到尾顺序读取,不支持随机跳转。这保证了读取可以在极简环境(例如从裸机扇区读取)中不依赖复杂的寻址逻辑。

## 3. HEADER 详细定义

### 3.1 字节偏移

```
偏移    宽度    字段名              值 / 含义
────────────────────────────────────────────────
0x00    4       magic               真实 CPU 指令序列(见 §1 执行入口)
0x04    2       version             当前 = 0x0004(版本 ≥ 4 强制真实魔数)
0x06    1       type                文件类型(见 §3.2)
0x07    1       arch_hint           创建者架构提示(见 §1 选择策略表末列)
0x08    4       flags               文件标志位(见 §3.3)
0x0C    2       count               容器条目数(N)
0x0E    2       header_crc          header 自身 CRC-16-CCITT
```

**关键变更(version ≥ 4)**:
- arch_hint 字段还原创建者是在什么架构上写的这个文件。值为:0x01=x86-64,0x02=AArch64,0x03=RISC-V,0x04=WASM,0x00=未标注
- version 上升到 0x0004(因为此变更不兼容 version ≤ 3)

### 3.2 文件类型 (type)字段

| 值 | 标识 | 内容用途 |
|----|------|----------|
| 0x01 | `FQMT_TYPE_STATE` | 表格编程的状态存储(15 列值) |
| 0x02 | `FQMT_TYPE_CONTAINER` | 单个 mlll 容器槽的保存 |
| 0x03 | `FQMT_TYPE_BELIEF` | 信念目标的导出(包含推导链) |
| 0x04 | `FQMT_TYPE_VIEW_LOG` | 视角切换日志 |
| 0x05 | `FQMT_TYPE_SNAPSHOT` | 全身快照(包含所有容器+日志链+状态) |
| 0x06 | `FQMT_TYPE_MORPHISM` | 态射代数快照 |
| 0x07 | `FQMT_TYPE_SHELL` | 蚕蛹壳表面签名模板 |
| 0x08 | `FQMT_TYPE_QA_CHAIN` | 问答推导链的归档 |
| 0x09 | `FQMT_TYPE_TABLE` | 表格编程的显式格式 |
| 0x0A | `FQMT_TYPE_TWIN_FORK` | 信念分叉的双路径保存 |
| 0x10 | `FQMT_TYPE_EXTENSION` | 扩展类型, header 后跟随一个类型扩展名 |
| 0x11..0x1F | *(私有保留)* | 满全法私有类型 |

> **类型 0x10 扩展格式**:当 type == 0x10 时, header 扩展 16 字节,在第 0x10 偏移处跟随一个 16 字节的字面类型名(ASCII,不足部分补 0x00)。这使系统能向后兼容地引入新类型而不浪费类型码空间。扩展类型名如表:
>
> | 扩展名(16字节) | 对应外部关联 |
> |----------------|-------------|
> | `loli\0...` | 早期遗留名称保留 |
> | `cocoonet\0...` | 蚕蛹壳元数据 |
> | `gtti\0...` | 字音态射显式保存 |
> | `chu\0...` | 岔途因果段单独导出 |
> | `mltti\0...` | 牺牲机制专用格式 |
> | `ysyt\0...` | 阴阳态聚合 |
> | `aide\0...` | 辅助容器块 |
> | `atoti\0...` | 辅助反栖态 |
> | `aitti\0...` | 辅助态射 |

### 3.3 标志位 (flags)

`flags` 是 32 位标志位掩码:

```
位 0 (0x00000001): ENCRYPTED     容器内容已加密
位 1 (0x00000002): COMPRESSED    容器内容已压缩(算法由 §9 定义)
位 2 (0x00000004): SIGNATURED    携带发送方的容器签名
位 3 (0x00000008): INCREMENTAL   这是增量快照(仅自上次以来变更的部分)
位 4 (0x00000010): EPHEMERAL     临时文件,不应被长期存储
位 5 (0x00000020): TOMBSTONE     已删除的容器墓碑(保留结构,内容为空)
位 6 (0x00000040): FORK_TWIN     包含信念分叉的 twin 路径
位 7 (0x00000080): VIEW_LOCKED   文件中所有容器的站位已被锁定
位 8 (0x00000100): WITNESSED     文件中所有关系都有见证者签名
位 9-31:                             保留,必须 = 0
```

## 4. 容器条目结构

### 4.1 容器通用头

```
每个容器条目都以一个 12 字节的本地头开始:

偏移    宽度    字段名              含义
────────────────────────────────────────────
0x00    2       cell_coord         SMRL 坐标(0..251)
0x02    1       view_flags         视图标志包(见 §4.2)
0x03    1       reserved           0x00
0x04    4       data_length        容器实际数据的字节数(不含头)
0x08    4       data_crc           CRC-32(data)
```

### 4.2 view_flags 结构

`view_flags` 是 8 位打包字段,与 SMRL cell 中的嵌入位对齐:

```
位 1-0:     站位标志 (与 SMRL cell 的 polarity[7:6] 同步)
    00 = 站位未声明
    01 = 有站
    10 = 无站
    11 = 空质壳
位 2:       站位锁定
位 3:       镜像占用
位 5-4:     调包深度 (0-3)
位 6:       见证过(= 1 时此容器在写入文件时已被至少一位见证者确认)
位 7:       保留
```

### 4.3 容器数据体

`data_length` 字节长的数据体。解释取决于文件类型:

**文件类型 = FQMT_TYPE_STATE (表格编程)**
```
数据体结构:
  [0x00] 2 bytes:         行序号(表格编程中的 C1)
  [0x02] 8 bytes:         SMRL cell 编码(64 位,大端序)
  [0x0A] 2 bytes:         C14 回答的字节长度(L_a)
  [0x0C] L_a UTF-8 bytes: C14 回答文本
  [0x0C+L_a] 2 bytes:    C15 信念目标的字节长度(L_b)
  [...+2]   L_b UTF-8 bytes: C15 信念目标文本
  后续:各行循环
```

**文件类型 = FQMT_TYPE_BELIEF**
```
数据体结构:
  [0x00] 2 bytes:           信念目标条数
  每条:
    [+2]     4 bytes:        信念来源行序号
    [+6]     2 bytes:        推导链字节长度(L_chain)
    [+8]     L_chain 字节:   参与此信念推导的列编号序列(如 C2,C3,C7,C14 → 字节序列 2,3,7,14)
    [+8+L_chain] 2 bytes:   信念文本字节长度(L_b)
    [...+2]  L_b UTF-8 bytes: 信念文本
```

**文件类型 = FQMT_TYPE_SNAPSHOT (全身快照)**
```
数据体结构:
  [0x00]    2 bytes:  表格编程行数(N_tab)
  [0x02]    2 bytes:  mlll 已用槽数(N_mlll)
  [0x04]    4 bytes:  自举 tick 计数
  [0x08]    4 bytes:  当前 surplus × 1000(定点小数,保留 3 位)
  [0x0C]    4 bytes:  文件创建时间戳(满全法内部 tick,非 UTC)
  
  然后是 N_tab 个表格行(格式与 FQMT_TYPE_STATE 相同)
  然后是 N_mlll × 64 bytes 的 mlll cell dump
  然后是 4 bytes 的空壳数量 + N × 16 bytes 的表面签名
```

## 5. TRAILER 文件尾

```
偏移 -4 (从文件末尾向前 4 字节):

宽度    字段名             值
──────────────────────────────
4       file_digest        CRC-32(文件中自 header 之后到 trailer 之前的所有字节)
```

如果文件被截断或被篡改,digest 校验会失败。

---

## 6. CRC 算法定义

### 6.1 header_crc (CRC-16-CCITT)

- 多项式: 0x1021
- 初始值: 0xFFFF
- 输入反射: 否
- 输出反射: 否
- 最终异或: 0x0000
- 覆盖范围: header 偏移 0x00..0x0D (14 bytes,即除 crc 字段外的全部 header)

### 6.2 data_crc (CRC-32)

- 多项式: 0x04C11DB7
- 初始值: 0xFFFFFFFF
- 输入反射: 是
- 输出反射: 是
- 最终异或: 0xFFFFFFFF
- 覆盖范围: 容器数据区的全部字节

### 6.3 file_digest (CRC-32)

与 data_crc 相同的参数,覆盖范围:自 header magic 到 trailer 前的所有字节。

## 7. 字节序

所有多字节字段采用**大端序**(Big-Endian,网络字节序)。

```
例外:容器内容体的 UTF-8 字符串不使用大端序。UTF-8 是字节流,无序问题。

例外:标记为 INCREMENTAL(增量)的文件可以是大端序也可以是小端序,由创建时所在 CPU 决定。但 header 的 magic 和 version 始终是大端序。

为什么选择大端序:大端序的字段在逐字节阅读时,高字节在前,这符合"从整体到局部"的读取惯性和人类的书写顺序。
```

## 8. 扩展容器:IDENTITY_BLOCK

### 8.1 用途

当文件需要标记自己的"是谁的"(即锚点的签名)时,在 header 之前额外开一个 IDENTITY_BLOCK:

```
偏移    宽度    字段名              含义
────────────────────────────────────────────
-0x20   4       id_magic           0x49444E54 ("IDNT")
-0x1C   2       id_version         1
-0x1A   4       id_anchor_type     0x52307072(内圈) / 0x4C307878(外圈) / 0x52307878(自我)
-0x16   8       id_hash            锚点哈希(SHA-256 的前 8 字节)
-0x0E   2       id_extent          扩展长度(0 = 无扩展)
-0x0C   4       id_block_crc       block 自身 CRC-32

[value of id_extent bytes ...]
```

IDENTITY_BLOCK 是**反向偏移**的——它的 header 在文件最前面, magic 在偏移 0。这使得读取者从文件第一字节就能同时判断"是不是 FQMT" 和 "是不是有身份签名"。

当 IDENTITY_BLOCK 存在时,header 的 `flags` 位 2(SIGNATURED) 必须 = 1。

## 9. 压缩算法

当 `flags` & COMPRESSED 时,容器数据区的所有字节(不含头)被压缩后再存储。

压缩算法标识字节紧跟在 header 后面(即取代原第一容器的前 1 字节),但更明确的方案是:固定使用**LZ4 快速压缩**。

```
压缩前:
  [ header (16) ] [ container1 ] [ container2 ] ... [ containerN ] [ trailer ]

后(仅压缩 container 数据部分,即每条容器条目的 data_length 部分):
  [ header (16) ] [ compression_algo_id (1) ] [ compressed containers blob ] [ trailer ]

compression_algo_id:
  0x01: LZ4(level 1 - fast)
  0x02: LZ4-HC(level 9 - high compression)
  0x03: ZSTD(level 3)

压缩仅接受开源压缩库,但压缩结果被完全包裹在 FQMT 内部——不依赖外部暴露任何约定。
```

## 10. 读取流程

```
read_fqmt_file(filepath):
  ① 读取 header,验证 magic == 0x46514D54
  ② 验证 version 在当前解析器支持范围内(version ≤ 当前解析器版本)
  ③ 计算 header_crc,比对 header 声明的 header_crc;若不匹配 → 拒绝读取
  ④ 根据 type 值选择读取路径(§4.3)
  ⑤ 对于每个容器条目:
     ⑤.1 读取容器通用头
     ⑤.2 读取 data_length 字节的数据
     ⑤.3 计算 data_crc,比对容器头的 data_crc;若失败 → 跳过此容器,记录错误日志
     ⑤.4 容器数据按 type 解释(见 §4.3)
  ⑥ 读取 trailer,计算 file_digest;若失败 → 文件损坏警告,但仍输出已读到的有效数据
  ⑦ 如果 flags & INCREMENTAL:
     在应用变更前,查找并先应用上一轮的上一快照文件
```

**部分损坏的宽容**:如果一个容器的 data_crc 失败,只跳过这一个容器,继续读取下一个——这保证了单个扇区损坏不会导致整个快照文件不可用。

## 11. 写入流程

写 FQMT 的过程不是一次性生成文件。采用**两防写入(写入临时文件 + 重命名)**:

```
write_fqmt_file(filepath, containers[], view_snapshots[], opts):
  ① 如果文件 flags & ENCRYPTED:先收集所有容器数据,加密后再写入
  ② 否则:先写临时文件 filepath + ".tmp"
  ②.1 写入 header (暂不填 header_crc,预留为 0)
  ②.2 写入每个容器条目 (逐个)
  ②.3 写入 trailer
  ②.4 回退到偏移 0x0E,填入 header_crc
  ②.5 重命名为 filepath
  
  [重命名完成后,文件对外可见]

  ③ 计算 file_digest,填充 trailing 4 字节
  
  ④ 如果 opts & VERIFY:
     立刻调用 read_fqmt_file 读取刚文件,验证三个 CRC 全部匹配
```

写入失败的保护:如果步骤 ② 至 ③ 之间发生断电或崩溃,.tmp 文件残留但正式文件不存在 → 读取者不会误读。下一轮写入前清理所有 .tmp 文件。

## 12. 与有/无关系

FQMT 文件是有/无状态的"时间切片"。

```
每次有/无切换的日志:
  格式:type = FQMT_TYPE_VIEW_LOG
  内容:固定宽度的环形缓冲,每条    <tick:4> <cell_coord:2> <view_before:1> <view_after:1>
  
为什么要独立成一种类型而不是嵌入在 KV 里:视角切换是系统的高阶历史,不属于一次性操作,需要长期保存并供审计。单独的 VIEW_LOG 类型允许读取者快速读取一条容器的全部站位变化历史,而不必遍历整个快照序列。

VERSIONED SNAPSHOT 推荐频率:
  - 常规:每 64 个 tick
  - 切换后:立即写一次增量(flags |= INCREMENTAL)
  - 分叉后:Duel 结果出来时立即写一次增量
  - 蜕皮后:立即写一次完整的 EPHEMERAL 快照并立刻替换上一个正式快照
```

## 13. 不变量

1. **Magic 必须是真实 CPU 指令**:版本 ≥ 4 的文件 magic 字段必须是一个真实可执行的 CPU 指令序列。不可使用 ASCII 文本作为魔数。这是 FQMT 4.0 的核心约束——文件头本身必须是可执行的入口代码。
2. **Legacy 兼容**:版本 ≤ 3 的文件可能仍含 "FQMT" 文本魔数(0x46514D54),但读取者应标记 deprecation 警告,并不再将此格式用于新建文件。
3. **版本兼容性**:高版本 reader 可以读低版本数据文件(version N 的 reader 可以读 version 1..N 的文件)。低版本 reader 不能读高版本文件(必须拒绝,不猜测)。跨大版本(≤3 ↔ ≥4)需要通过 Legacy 路径处理。
4. **CRC 三检查**:header / data / trailer 三处 CRC 必须各自校验——任何一处失败都视为局部失败,不应当整体拒绝(除了 header 校验失败)
5. **容器原子性**:每个容器条目要么完整存在(data_crc 通过),要么不存在。不承认部分写入的容器。
6. **类型决定解释**:同一段字节在不同 type 文件中有不同意义。文件类型被恶意篡改时解释出无结构但不崩溃——因为 data_length 和 CRC 保证了读不会越界。
7. **不涉及外部标识符**:FQMT 内部不出现任何外部系统的 MIME / HTTP / URI / 除满全法以外的 UUID。如果需要指向外部,由外表面层在外部世界和 FQMT 之间做桥接。
8. **魔数平台识别优先级**:读取者应按照 §1 选择策略中列出的顺序判断魔数,不按字符串比对。同一逻辑语义在不同平台上有不同魔数编码——这是设计意图,不是格式错误。
