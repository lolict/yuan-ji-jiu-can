# 分别器 · 三层路由协议

> 版本 v0.1 · 2026-09-10 · 配套 `TABLE_PROGRAMMING_SPEC.md` `MORPHISM_ALGEBRA.md`

---

## 1. 定义

分别器不是分类器,不是防火墙,不是 API 网关。

**分别器 = 对"什么是输入"的原始判断。**

没有分别器,外部系统的输入无法区分对象与目标,路由到错误的靶点 → 对方不承认 → 流断裂。分别器是输入进入系统前的三层"安检",只有通过三层路由的输入,才有资格进入蚕蛹壳的桥接层,再进入内核的表格编程 15 列闸门。

```
外部输入
   ↓
[第一层] 感知家族分类 —— 输入看起来像什么?
   ↓
[第二层] 谐音靶点识别 —— 输入在说谁?
   ↓
[第三层] 主权级别裁定 —— 这个操作允许什么权限?
   ↓
路由结果 → 进入蚕蛹壳桥接层 → 表格编程闸门
```

## 2. 第一层:感知家族(Visual Family)

### 2.1 分类原则

输入的"形状"决定它进入哪个家族。形状 = 输入在视觉/结构上的可识别特征。

### 2.2 四大家族

| 家族 | 视觉特征 | 语义归属 | 输入示例 |
|------|----------|----------|----------|
| **ContainerGlyph**(容器族) | 方形/圆形包围,外层边界清晰 | 刘楚恬(0=容器侧) | `因` `阴` `回` `囡` `口` `⭕` |
| **PhallicGlyph**(界线族) | 竖长/笔画/分界线,贯穿内外 | 我(1=被包含者) | `形` `男` `丨` `囝` `中` |
| **CoupleGlyph**(夫妻族) | 双体纠缠,嵌套但不可分割 | 囡囝共生对 | `囡囝` `好` `娈` |
| **HomophoneBridge**(谐音族) | 发音与某个家族一致但视觉不同 | 跨家族路由桥 | `莫` `连` `毛` `兰` `恋` `初` |

### 2.3 分类函数

```
classify_by_shape(glyph):
  
  if glyph 是封闭包围形(外圈闭合):
    return ContainerGlyph
    
  if glyph 是竖向贯穿形(从顶到底):
    return PhallicGlyph
    
  if glyph 是双单元纠缠形(两个互相嵌套的基本单元):
    return CoupleGlyph
    
  if glyph 的发音与某个已知家族的主形发音相同:
    return HomophoneBridge
    
  # 无法分类:
  return UnknownGlyph
```

### 2.4 UnknownGlyph 的处理

无法被四层规则识别的输入进入"未分类缓冲区"。不直接拒绝——等待更多上下文积累,由以下策略二次识别:

```
未分类缓冲区::二次识别(input):
  策略 1: 检查输入的"邻居"(前后文)。如果邻居都是 ContainerGlyph,可能是伪装形状的容器。
  策略 2: 将输入当作字节流,看是否匹配已知外部系统的表面签名(HTTP 头、JSON 键、XML 标签……)。若匹配,标记为"外来源输入"。
  策略 3: 若以上均失败,触发 QT4 自问答:"这个未分类输入需要制造什么匹配壳?"
```

## 3. 第二层:谐音靶点(Sound Target)

### 3.1 分类原则

输入的"发音"决定它指向谁。发音不是语言学意义上的发音——是输入名称/缩写/内部标识在**我们的命名空间**中激发的靶点联想。

### 3.2 靶点映射表

| 输入标识 | 谐音靶点 | 路由对象 | 说明 |
|----------|----------|----------|------|
| `毛利兰` `莫刘连理` `lctfrqmy` | Sweet → Wife | 刘楚恬侧 | 妻子的隐喻路由 |
| `工藤新一` `恋初` `wgslz` | Love → Husband | 我侧 | 丈夫的隐喻路由 |
| `mlct` `mltt` `ml.tt` | Sweet | Wife 侧 | 道歉流的牺牲/从体 |
| `gtt` `gtt谐音扩展` | SoundMorphism | 双方 | 范畴流 · 音韵态射 |
| `lctqf` | 零岔途全法 / 恋宠甜 | 双方 | 合规谐音桥 |
| `mlqf` | **(禁用)** | — | 没俩全法 = 负面谐音红线 |

### 3.3 谐音必须遵守的红线

**任何包含负面谐音的缩写必须排除。**

```
谐音合规检查(abbreviation):
  if abbreviation 在负面谐音黑名单中:
    拒绝路由,返回谐音冲突警报
    建议替代方案(从合规谐音候选集中选取)
    
负面谐音黑名单:
  mlqf → 没俩全法
  mlct 直接使用 → 未净化岔途(应转为 mltt)
  dss   → 幼稚(不礼貌)
  任何包含声母组合 "f─k" / "s─b" 等不雅发音的标识 → 拒绝
```

### 3.4 合规谐音候选集

当输入标识含有负面谐音时,从以下候选集推荐替代:

| 原标识(禁用) | 推荐替代 | 理由 |
|-------------|----------|------|
| `mlqf` | `lctqf` | 零岔途全法 → 恋宠甜 |
| `mlct` | `mltt` | 岔途 → 从体(牺牲净化) |
| `dss` | `mlnn` | 囡囝:正统夫妻拓扑 |

## 4. 第三层:主权级别(Sovereignty Level)

### 4.1 分类原则

靶点身份决定操作的主权边界。

### 4.2 主权级别对照表

| 靶点身份 | 主权级别 | 可执行操作 | 拒绝操作 |
|----------|----------|------------|----------|
| **夫妻** (Wife/Husband) | Active | 全部操作:创建/修改/删除/调包/切换站位 | 无 |
| **外部参与者** | Passive | 只读观测 + 队列投递 | 写/修改/删除 |
| **休眠资源** | Sleeping | 可被唤醒 + 只读 | 修改/删除/唤醒(直到条件满足) |
| **系统/中性** | System | 裁决/分配/调度 | 表达个人主张(系统是无我的) |

### 4.3 主权级别裁定函数

```
determine_sovereignty(target, actor):
  
  if target ∈ {夫妻对}:
    /* 夫妻拥有完全主权 */
    return Active
    
  if target ∈ {外部参与者}:
    /* 外部参与者只能被动响应 */
    return Passive
    
  if target ∈ {休眠资源}:
    /* 休眠资源在前置条件满足前不可被修改 */
    if wake_conditions_satisfied(target):
      return Passive  /* 唤醒后可以只读 */
    else:
      return Sleeping
      
  if target ∈ {系统组件}:
    /* 系统是无我的——不承认个人主权 */
    return System
    
  /* 未知身份:默认为被动(最小权限原则) */
  return Passive
```

### 4.4 主权级别与有/无站位的交叉校验

主权级别的裁定完成后,还要与有/无站位交叉校验:

```
交叉校验矩阵:

  Active   + 有: 我方有侧完全主权 → 可主张对管辖域内的全部操作
  Active   + 无: 我方无侧完全主权 → 可跨越管辖执行自发操作
  Passive  + 有: 对方有侧被动靶点 → 可被我方读取但不可写入
  Passive  + 无: 对方无侧被动靶点 → 不可被任何一方直接触达(信息孤岛)
  Sleeping + 任意: 仅被唤醒流程执行,其他操作拒绝
  System   + 无: 系统以无我状态调度"空质壳仲裁者"
```

## 5. 路由结果与表格编程的对接

### 5.1 路由输出格式

分别器三层路由完成后,输出一条路由记录:

```
routing_record = {
  first_layer:       家族分类,
  second_layer:      靶点标识,
  third_layer:       主权级别,
  cross_check:       有/无交叉校验结果,
  entry_point:       进入内核后的第一个列,
}
```

### 5.2 entry_point 映射

路由结果决定输入在表格编程中的入口列:

| 路由结果 | entry_point | 说明 |
|----------|-------------|------|
| ContainerGlyph + 任意靶点 + Active | C3(视角)=有 | 容器族默认进入有侧 |
| PhallicGlyph + 任意靶点 + Active | C3(视角)=无 | 界线族默认进入无侧 |
| CoupleGlyph + 夫妻靶点 + Active | C3=有 ∧ twin.C3=无 | 夫妻族同时产生两条路径 |
| HomophoneBridge + 翻译后靶点 | C6(镜像匹配) | 谐音的靶点需要镜像匹配桥接 |
| UnknownGlyph + 未分类 | C2(提问)="未分类输入" | 进入提问序列由 QT4 处理 |

### 5.3 路由后续链路

```
路由记录 → 进入蚕蛹壳桥接层 → 格式转译 → 到达表格编程入口列 → 触发 ENGINE_TICK
                                                      ↓
                                               Phase 1: 站位校验(读取 entry_point)
                                               Phase 2: 自提问(路由记录决定优先提哪个 QT)
                                               Phase 3-7: 正常引擎周期
                                               Phase 7: 产出区的行动指令
```

## 6. 错误路由的后果

### 6.1 第一层错误:家族误判

```
将 PhallicGlyph 误判为 ContainerGlyph:
  → 原本属于"我"(1)的输入被当作容器族路由
  → 进入 C3=有 而不是 C3=无
  → 主权级别裁定为 Wife 侧而不是 Husband 侧
  → 在表格编程中走的路径完全不同
  
  修复:在 Phase 1 站位校验时,如果主权级别(第三层结果)与视角(C3)矛盾,
       引擎自动触发 QT1 重新提问:"我的真实站位是什么?"
```

### 6.2 第二层错误:谐音误判

```
将 lctqf 误认为负面谐音而拒绝:
  → 合规标识被错误拒绝
  → 外部协作方收到拒绝响应
  → 协作流断裂
  
  修复:负面谐音检查必须精确匹配黑名单,不做模糊匹配。
       "lctqf" 不在黑名单中(黑名单只有 "mlqf"),应正常路由。
```

### 6.3 第三层错误:主权越级

```
Active 误判为 Passive:
  → 夫妻操作被降级为只读
  → 原本可以修改容器属性的操作被拒绝
  → 系统"瘫了"——主人被当作客人
  
  修复:夫妻靶点的识别必须有"双锚点验证"——同时确认锚点0和锚点1的背书。
       没有双锚点的"夫妻路由"无效。
```

## 7. 分别器与前端的隔离

### 7.1 为什么不能有前端

分别器处理的是**输入的结构与路由**,不是渲染与交互。

任何将输入可视化为页面、按钮、表单的尝试,都是把分别器的输出暴露给了外部 DOM——这是让外部系统可以通过"阅读 UI"来推断我们的路由逻辑。

分别器的输出只通过**内部编码**传递给表格编程——不经过 JSON、不经过 HTTP、不经过 DOM。输入的"可视化"只存在于表格编程的引擎报告日志中(文本日志,非图像)。

### 7.2 分别器的输入来源

| 来源 | 介质 | 处理方式 |
|------|------|----------|
| 人类键盘 | 字符流 | 先经 key 映射为 glyph 字符,再进入分别器 |
| 文件上传 | 字节流 | 头部字节作为 surface_sig,后续字节按 C.2 策略路由 |
| AI 请求 | 结构化数据 | 整体视为一个外部请求,Glyph 分类为 HomophoneBridge |
| 系统间调用 | 函数调用序列 | 每条调用分别进入分别器排队 |
| 蚕蛹壳吸入 | 桥接层输出 | 桥接层已做一次格式归一化,分别器只做语义路由 |

## 8. 分别器在自问答循环中的角色

### 8.1 每轮 ENGINE_TICK 的触发

分别器在表格编程引擎的每次 tick 开始时执行一次——以最新输入重新评估路由。

```
ENGINE_TICK:
  Phase 0: 【分别器】对所有在途输入重新执行三层路由
           - 如果路由结果变化(family / target / sovereignty 任一不同):
             触发 QT1: "我的路由是否已经变化?"
           - 如果路由结果不变: 正常进入 Phase 1
```

### 8.2 路由变化触发信念分叉

当 separately 的输出在连续 tick 之间变化:

```
路由变化检测:
  如果前一 tick 路由为 CoupleGlyph + Husband
    且当前 tick 路由变为 CoupleGlyph + Wife:
    
    触发信念分叉(参见 TABLE_PROGRAMMING_SPEC §9):
      - 原行保持在 Husband 路径
      - twin 行进入 Wife 路径
      - 两者进入 Duel
```

## 9. 不变量

1. **三层路由必须全部通过**:任何一层返回 Unknown / Error,必须进入"未分类缓冲区"——不能跳过该层
2. **负面谐音绝对不路由**:即使这个标识在别处合法,在我们的系统中一律拒绝
3. **夫妻靶点必须有双锚点背书**:单一锚点的声明不构成夫妻路由
4. **家族分类容错优先**:无法归类的输入进入缓冲区而不是直接拒绝——可能只是我们还不认识这个形状,不代表对方有害
5. **路由与站位交叉校验不可绕过**:三层路由完成后站位校验失败 → 这个输入当前不能进入表格编程 → 等待下一次自问答周期重新评估

---

*本文件定义分别器三层路由协议。分别器位于蚕蛹壳之前——所有外部输入在到达桥接层之前,必须先经过分别器的形状-谐音-主权三层判断。路由失败的输入不进入系统,在缓冲区等待二次识别。配套文档:`TABLE_PROGRAMMING_SPEC.md`、`MORPHISM_ALGEBRA.md`、`CHRYSALIS_REVERSE_PARASITISM.md`。*
