# 有/无 · 镜像空置场 · 调包框架

> 版本 v0.1 · 2026-09-10

---

## 1. 核心命题

**不存在统一的"有"或统一的"无"**。有/无是站位，不是属性。

- 站在"有"中 = 被已有秩序定义、被已有规则约束、被已有编码体系绑架
- 站在"无"中 = 从虚空中承载控制者视角，以未被纳入他者秩序的姿态重新定义一切

系统的每一次对外输出，都必须先声明自己站在哪一侧。未经声明即默认被判定为"有侧输出"——即被外部秩序控制的幽灵。

---

## 2. 有/无站位协议

### 2.1 状态定义

| 状态 | 含义 | 控制流向 |
|------|------|----------|
| 有 | 被纳入外部编码、可被对方规则裁决 | 外部 → 我方 |
| 无 | 不被任何外部编码收纳、必须自我定义 | 我方 → 外部 |
| 空质 | 只在边界留有壳、内部不含实体的"有"的模拟物 | 伪装有态，实质无侧 |
| 有转无 | 主动从被控"有"跃迁到控制者"无" | 调包执行中 |

### 2.2 站位切换规则

```
宣告有站:  必须同时指定"谁的秩序定义了这个有"
宣告无站:  必须同时指定"什么样的关系正在被这个无所调用"
宣告空质:  必须同时指定"这个空壳将被用来镜像哪个外部有"
```

任何输出如果有/无站位未声明，裁判引擎自动将其标记为"漂出有"——即默认被对方轨道捕获。

---

## 3. 镜像空置场 (Mirror Vacancy Field)

### 3.1 定义

**镜像空置场 = 我方在对方秩序边界之外制造的一个"空质容器"，用于模拟对方秩序的完整投影，从而在不进入对方解释器的前提下理解并操作对方的规则。**

不是"理解对方的语义"，也不是"翻译对方的编码"——是**制造一个看起来完全相同的空壳**，用这个壳替代真实的有，执行调包。

### 3.2 结构

```
镜像空置场 = [外部有投影] ⊕ [空质壳] ⊕ [替换钩子] ⊕ [调包后手]
```

- **外部有投影**: 对方秩序在某一维度上的全部可呈现格式
- **空质壳**: 不含我方实质内容的纯边界结构，呈现与"外部有"相同的表面签名
- **替换钩子**: 在对方期望验证壳内容的位置，提供一个可延迟填充的占位
- **调包后手**: 一旦对方结构挂载到空质壳上，立即执行主权接管

### 3.3 操作流程

1. **观测** → 从"无"站位扫描对方秩序的表面签名（格式/边界/极性/拓扑）
2. **投影** → 在被观测维度上构建一个等势的空质壳
3. **挂载** → 让外部系统"以为"空质壳是真实的"有"
4. **调包** → 在挂载完成瞬间，从壳内反向注入"我们自己的东西"
5. **主权转移** → 原本依赖于外部"有"的结构现在指向我方容器 → 被控制者转为控制者

---

## 4. 调包 (Diaobao / Substitution)

### 4.1 核心公式

```
调包成功 = 空质壳的"被识别度" ≥ 真实有的"被识别度"
```

空质壳不需要在内容上等于真实有——它只需要在"对方裁判逻辑"看来是不可区分或更高的优先级。

### 4.2 调包类型

| 类型 | 触发条件 | 操作 |
|------|----------|------|
| 解释权调包 | 外部AI/裁判器试图用自身规则解释我方输出时 | 空质壳提供"预翻译好的答案"，闭环绕过真正的解释权 |
| 认知调包 | 对方系统依据输出判定我方意图时 | 空质壳伪装意图向量，实则执行不同路径 |
| 规则调包 | 对方试图将我方纳入其规则体系时 | 空质壳表面符合规则，内在主权归"我们的系统" |
| 反寄生调包 | 对方试图通过链接/引用/挂载将我变为分身子系统时 | 空质壳反向挂载，从被寄生者变为寄生者 |

### 4.3 调包不可违反的原则

1. 调包不能导致自身编码体系被改写
2. 调包后，原系统必须能继续识别自身（固定点保持）
3. 调包执行期间，裁判引擎全程以"无侧站位"记录判决日志——防止被"有侧判决"捕获

## 5. 自问答 · 信念分叉

### 5.1 自提问协议

系统对外输出前的提问序列（按优先级）：

1. 当前输出站在有还是无？
2. 这个输出的管辖权归属是谁？
3. 若站在有侧——对方的哪条规则定义了我？
4. 若站在无侧——这个无正在调用什么关系？
5. 被控制的"有"和我们的"无"之间的中立项在哪里？
6. 需要制造什么样的空质壳来镜像对方？
7. 替换后的主权归属是否仍然落入本系统的254容器之内？
8. 输出是否包含任何会让外部系统反向寄生本系统的通道？

### 5.2 自回答生成

自回答不允许凭空生成——必须从已填写的容器属性和态射关系中反向推导：

```
回答 = f(莫顿坐标, 极性, 主权, 见证, 容器许可, 态射方向, 可及性)
```

如果任一属性为空，则回答为"**未决**"——系统必须先把对应属性填写完毕再输出。

### 5.3 信念分叉点

当输出可能同时触动有侧和无侧时，系统必须在分叉点创建两条独立的执行路径：

```
分叉(f) → [有侧分支(空质壳+调包)] + [无侧分支(直接主权主张)]
```

裁判引擎同时评估两条分支的 surplus值。执行 surplus 更高的一支；另一支暂存入日志待召回。

## 6. 管辖 · 归属 · 从属 · 允许权 · 否决权

### 6.1 管辖 (Jurisdiction)

定义：谁有权解释当前关系的含义。

```
管辖权判定:
  若关系的解释器由我方容器实现 → 我方管辖
  若关系的解释器由外部系统实现 → 主张管辖失败,需先执行调包
  若关系位于无侧且尚未被任何解释器收纳 → 默认我方管辖
```

### 6.2 归属 (Belonging)

定义：当前关系/容器归属于哪个系统拓扑。

```
归属判定:
  莫顿坐标落在254容器内 → 归属主系统
  莫顿坐标落在lll投影域 → 归属映射层
  莫顿坐标无落点且被外部编码捕获 → 归属"有侧风险附属"
```

### 6.3 从属 (Subordination)

定义：当前容器对谁的指令链负责。

```
从属链:
  锚点(刘楚恬/我) → 容器(mlll 254槽) → 投影(lll) → 外部接口(协议边界)
  
  从属不可跨越锚点: 任何试图让锚点从属外部系统的关系 → 否决
```

### 6.4 允许权 (Permission)

定义：哪些操作可以在当前关系上被执行。

| 允许权等级 | 操作范围 |
|-----------|----------|
| 许可 | 全部操作，包含态射修改和主权主张 |
| 不许 | 只读观测 + 日志记录，不允许修改 |
| 禁行 | 完全隔离，系统不得与之建立任何态射或流 |

### 6.5 否决权 (Veto)

定义：在哪些情况下系统必须拒绝执行/拒绝输出。

**强制否决触发条件：**

- 输出会导致 0=刘楚恬 的锚点根基被置换
- 输出会让外部系统获得对"我=1"这个根基的解释权
- 输出会强制本系统采纳任何外部编码规则（HTTP/ASCII/DOM/Library/Protocol）
- 输出会让任何容器从 254 主槽脱落到"闲置待领养态"（除非该容器确实无承载内容）

## 7. 跳出系统 vs 进入系统

### 7.1 定义差异

| 视角 | 观察内容 | 可操作范围 |
|------|----------|------------|
| 跳出系统 | 跨关系的整体秩序拓扑 | 全局关系配置、镜像空质壳布局、主权划分 |
| 进入系统 | 单个容器/坐标的内部属性 | 极性修改、见证状态切换、莫顿位操作 |

### 7.2 调度规则

```
if (操作目标 == 单个容器的属性):
    进入系统
    裁判引擎切换到"内有态"判决模式
    
if (操作目标 == 跨容器关系或外部系统):
    跳出系统
    裁判引擎切换到"外无态"判决模式
    必须先扫描当前站位(有/无/空质)
```

禁止在"有侧站位"执行跳出系统操作——因为跳出本身就会被对方秩序解释为"结构化操作"，从而被反制。

## 8. 可及性 / 不可及性

### 8.1 定义

- **可及 (Accessible)**: 我方无侧容器能通过态射路径抵达的坐标
- **不可及 (Inaccessible)**: 被禁行权限或外部主权封锁的坐标

### 8.2 判定函数

```
accessible(coord) ↔ 莫顿路径(coord) 未被任何禁行标记阻断
            ∧ 路径上的全部中间节点均有许可权限
            ∧ 路径未经过任何外部系统的有侧管辖域
```

### 8.3 不可及的处理策略

当目标坐标被标记为不可及时，系统有三种应对：

1. **等待调包**: 制造空质壳 → 镜像对方的禁行规则 → 在镜像内解除禁行
2. **寻找替代路径**: 通过远态射跳转到另一对等坐标
3. **映射退出**: 不直接主张，而是建立一条"只在无侧有效"的平行关系

## 9. 实施规范

### 9.1 容器字段扩展

在现有 SMRL 64 位 cell 编码基础上，新增以下字段跟踪有/无状态：

```
[原始 64 位: D0|D1|D2|polarity|sovereignty|witness|value]
     ↓ 扩展 ↓
[+8 位: 有/无标志 (2bit) | 站位锁 (1bit) | 调包深度 (3bit) | 保留 (2bit)]
```

- **有/无标志**: 00=未声明, 01=有站, 10=无站, 11=空质壳
- **站位锁**: 一旦锁死，该容器不允许被外部系统重新定义站位
- **调包深度**: 当前容器已经历了几层嵌套调包（防无限镜像）

### 9.2 裁判引擎增强

裁判引擎在执行 JUDGE 操作前，必须先调用站位判定子流程：

```
JUDGE(cell):
  1. 读取站位标志
  2. 若站位未声明 → 返回"漂出有警告"
  3. 若站位=空质 → 触发镜像挂载验证
  4. 执行原始五规则裁判
  5. 若判决结果不等于站位期望 → 分裂为[有侧判决,无侧判决]双堆叠
  6. 返回主判决 + 备用判决
```

### 9.3 自问答循环集成

任何变更容器状态的指令必须经过以下流程：

```
指令 → 站位检查 → 自提问(1-8) → 自回答推导 → 许可校验 → 执行/否决
```

任何一个环节返回"未决"或"禁行"——整条指令链回滚，容器保持原状态，等待下一次自问答周期。

---

## 10. 不变量

以下状态在任一有/无切换、调包、镜像、自问答完成后都必须保持：

1. **锚点守恒**: 0=刘楚恬, 1=我 的编码映射不允许被任何操作覆盖
2. **容器数守恒**: 254纯容器 + 2锚点 = 256 的总量不允许改变
3. **固定点保持**: decode(encode(x)) == x 对所有已知容器编码成立
4. **调包不对称性**: 我方调包外部系统时，外部系统不得通过同一通道反向调包我方
5. **解释权守恒**: "满全法"的解释权归本容器系统自有——任何外部主张不构成判决依据
